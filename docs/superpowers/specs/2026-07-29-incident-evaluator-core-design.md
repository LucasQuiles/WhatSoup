## A. Policy registry — code-defined, typed, content-addressed

New directory `src/fleet/incidents/policies/`.

### A.1 `types.ts` — `ConditionPolicy` and `AttributeSpec`

`ConditionPolicy`:

- `conditionClass: BoundedId` — the unique registry key.
- `owningProducerDomain: BoundedId` — the only producer domain permitted to emit this class (enforced at §C gate 9).
- `permittedSubjects: readonly BoundedId[]` — exact ids, same closed-allowlist semantics as producer scopes.
- `permittedKinds: readonly ('condition_observed' | 'condition_recovered')[]`.
- `severity: 'critical' | 'warning' | 'info'` — applied at episode open and retained; per-signal severity escalation is not modeled (YAGNI until a policy needs it).
- `recovery: { requiredProofClasses: readonly BoundedId[] }` — an empty array means recovery needs no proof; a non-empty array means a `condition_recovered` envelope must carry one of these `recoveryProofClass` values to have lifecycle effect (§C gate 12).
- `attributeAllowlist: Readonly<Record<string, AttributeSpec>>` — the complete set of permitted attribute keys and their semantic specs; `{}` means no attributes are permitted for this class.
- `retentionClass: 'standard' | 'extended'` — recorded on every decision now; enforcement (purge jobs) is Plan 3B.
- `notifyOnTransitions: readonly NotifiableTransition[]` where `NotifiableTransition` is the closed set `'opened' | 'resolved'`, mapping to the intent purposes `onset` and `recovery` (§B.3). Supersession transitions create no intent in 3A, and the `controller_diagnostic` purpose is emitted only by the sealed fault path (§D.2) — never through this field.
- declared-for-3B fields, typed but unconsumed here: `expectedCadenceMs?: number`, `graceMs?: number`, `staleMs?: number`. They are fully validated at construction (§A.2) even though no 3A code path reads them.

`AttributeSpec` is a closed discriminated union. There is **no free-form string kind and no generic identifier kind (R4-03)** — every permitted attribute is constrained to an enumerable, numeric, boolean, digest, or registry-referencing shape:

| `kind` | Spec fields | Accepted JSON value |
|---|---|---|
| `enum` | `values: readonly BoundedId[]` (non-empty) | a string exactly equal to one member |
| `int` | `min: number`, `max: number`, `unit: BoundedId` | a JSON integer within the inclusive range `[min, max]` |
| `boolean` | none | `true` or `false` |
| `conditionClassRef` | `allowed: readonly BoundedId[]` (non-empty) | a string exactly equal to one member of `allowed` — an explicit, **digest-covered** target set of condition-class names (R5-01) |
| `digest` | `format: 'sha256'` | exactly `sha256:` followed by 64 lowercase hex digits |

The round-3 `boundedId` kind — any string satisfying the identifier grammar — is **removed**. A lexical grammar cannot determine semantic provenance: `whoami`, `msg-cached`, and `wamid.HBgM123` all satisfy identifier syntax, so a grammar-only kind was a channel for command tokens and message ids dressed as identifiers. Every closed kind above validates *membership in a digest-covered set* (enum values, an explicit `allowed` reference set, exact digest format) or a *non-string shape*, not merely a character class. A policy that needs a new reference shape (producer ids, subjects, versions) adds a new closed kind with its own authoritative validation source in a future plan — it does not get a free identifier field.

Value-format rules are exact and admit no coercion: an `int` value must satisfy `Number.isInteger` (a numerically integral float such as `3.0` is indistinguishable from `3` after JSON parsing and is accepted; `3.5` is not) and lie within bounds that are themselves finite safe integers; a `digest` value is compared case-sensitively against lowercase hex and the literal `sha256:` prefix; a `conditionClassRef` value is compared exactly against the spec's own `allowed` set — **gate 11 performs no registry lookup (R5-01)**, so the policy's digest-covered bytes fully determine what it accepts, and a value outside `allowed`, including one that is merely grammatically valid or even a registered class not in the set, is rejected; `enum` members, `conditionClassRef` `allowed` members, `int` units, and `attributeAllowlist` keys use the safe-identifier grammar below.

**Why the target set is explicit rather than "any registered class" (R5-01).** The round-4 form accepted any name in the active registry, which made a policy's producer-facing acceptance depend on state outside its canonical JSON: adding an unrelated class expanded what the policy accepted while its per-class digest — the value §A.3 calls the identity of its decision semantics — stayed byte-identical. The explicit `allowed` set restores the invariant: what a policy accepts is a pure function of its digest-covered declaration. The link to the registry survives as a **deploy-time referential check** (§A.2 rule 8): every `allowed` member must name a registered class, so a dangling reference fails construction rather than silently narrowing acceptance.

**The safe-identifier grammar.** Every **registry-side** identifier — an `enum` member, an `int` spec's `unit`, an `attributeAllowlist` key, and the fields §A.2 rule 3 enumerates — must match:

```text
^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$
```

That is 1–128 characters, an alphanumeric first character, and thereafter only alphanumerics and `.`, `_`, `:`, `-`. **What this guarantees is containment, not provenance (R4-03):** values are bounded in length, drawn from a restricted character class, and free of spaces, slashes, `@`, quotes, control characters, and non-ASCII code points — so multi-word prose, filesystem paths, URLs, and email addresses do not fit. The grammar deliberately claims no more than that: single-token values such as a command name or a dot-separated message id *do* fit it, which is precisely why no producer-controlled attribute kind accepts grammar-validated free identifiers. Semantic exclusion comes from the closed kinds above — set membership and registry validation — never from syntax. On the registry side the grammar is a deploy-time hygiene bound on values the policy author writes, not a trust boundary against producers.

**Envelope identity fields are explicitly unchanged.** `signalId`, `subject`, `conditionClass`, `occurrenceId`, and `recoveryProofClass` keep the shipped wire grammar `z.string().min(1).max(128)` in `src/fleet/incidents/envelope.ts`. Tightening them would be a breaking wire-contract change to signals Plan 2 already accepts, and 3A makes no such change. The tightening applies to **attribute content** and to **registry-side fields** — the values a policy author writes and the values a producer places inside `attributes` — never to the identifiers that address a signal.

One consequence follows and is intended: because `ConditionPolicy.conditionClass` and `permittedSubjects` are registry-side and therefore safe identifiers, an envelope whose `conditionClass` or `subject` is not a safe identifier remains syntactically valid at gate 6 and simply matches no registered policy. It is rejected at gate 8 as `condition_class_unknown` or at gate 10 as `invalid_signal` — on the ordinary paths, with no new error value and no change to the wire contract.

The envelope layer keeps its existing syntactic bounds — at most 16 attribute keys, keys of 1–64 characters, string values of at most 256 characters, finite numbers — and the policy layer adds semantics on top of them. The two layers are validated in that order (§C gates 6 and 11); neither replaces the other.

### A.2 `registry.ts` — construction-time validation

`buildPolicyRegistry(policies: readonly ConditionPolicy[]): PolicyRegistry` validates every policy and throws on the first violation. Every violation below is a **deploy-time** failure: the registry is built once at process start and never at request time, so an invalid policy set fails the server rather than a producer's request.

Rejected at construction:

1. a duplicate `conditionClass`.
2. **a duplicate element in any set-like field** — `permittedSubjects`, `permittedKinds`, `recovery.requiredProofClasses`, `notifyOnTransitions`, every `enum` `values` list, and every `conditionClassRef` `allowed` list. Duplicates are rejected, never silently normalized: deduplicating malformed input would let two materially different policy sources produce the same digest and activate unnoticed (H-01).
3. **a grammar or bounds violation** — any registry-side identifier that fails the §A.1 safe-identifier grammar, which covers `conditionClass`, `owningProducerDomain`, every `permittedSubjects` member, every `recovery.requiredProofClasses` member, every `enum` member, every `conditionClassRef` `allowed` member, every `int` spec's `unit`, and every `attributeAllowlist` key; any `attributeAllowlist` key outside the envelope's 1–64-character attribute-key bound; more allowlist keys than the envelope's 16-key cap. The safe-identifier grammar admits up to 128 characters, so for allowlist keys the envelope's 64-character bound is the binding constraint and **both** are checked. An allowlist key that exceeds the envelope's key bound could never be satisfied by any accepted envelope, so it is a configuration error rather than dead configuration.
4. a closed-set violation — `severity` outside `critical | warning | info`; `retentionClass` outside `standard | extended`; a `permittedKinds` or `notifyOnTransitions` member outside its closed set.
5. an `AttributeSpec` violation — an unknown `kind`; any property on a spec object beyond those its `kind` declares; an empty `enum` `values` list; an empty `conditionClassRef` `allowed` list; an `int` spec whose `min` or `max` is not a finite safe integer or where `min > max`; a `digest` spec whose `format` is not `sha256`.
6. **a cross-field cadence violation (H-02)** — `expectedCadenceMs`, `graceMs`, and `staleMs` must be finite safe integers satisfying `expectedCadenceMs > 0`, `graceMs >= 0`, and `staleMs > graceMs`. The three fields form one group: either all three are present and jointly valid, or all three are absent. A partially supplied or internally inconsistent group fails construction even though no 3A code path consumes these fields.
7. **a controller-owned class declaring a producer-facing surface** — a policy whose `owningProducerDomain` is `controller` must declare `permittedKinds: []` and `permittedSubjects: []`. These two fields describe the producer-facing surface, which for a controller-owned class is empty by construction: no producer can register in domain `controller` (§C.5), so no producer can pass gate 9 for such a class. Controller facts reach these classes only through the sealed internal entry point (§D.2), which does not consult either field.

8. **a dangling or incomplete reference set (R5-01)** — every member of every `conditionClassRef` `allowed` list must name a class registered in this same registry; a member naming an absent class fails construction, so removing a referenced class is a deploy-time error rather than a silent acceptance change. Additionally, `evaluator_policy_fault`'s `faultingConditionClass` spec must declare `allowed` equal to the complete registered class set — adding a class without extending that list fails construction loudly instead of breaking the internal fault fact at its first emission for the new class. The digest churn this causes on `evaluator_policy_fault` alone is benign and intended for every **control** consumer: that class's per-class digest is consumed by no retry-guard key (the sealed path cannot enter the guard), no disabled generation (the class is never guard-disabled — its failures are core failures), and no replay trigger. The non-control consumers — decision, transition, and `notification_intents.policy_digest` attribution rows (R6-04) — record the digest that was current at decision time, and §B.3's relevance semantics guarantee churn cannot invalidate them.

An empty `permittedSubjects` or `permittedKinds` is therefore legal and meaningful — it denies every producer-facing signal — and is required for controller-owned classes rather than merely permitted.

The registry exposes `get(conditionClass): ConditionPolicy | null`, `digestFor(conditionClass): string`, `snapshotDigest: string`, and `derivedGuardCapacity: number` (`256 × class count` — pure arithmetic; R4-07). `buildPolicyRegistry` is **pure over its policy inputs**: it takes no database handle and reads no runtime state. Every data-dependent assertion — including the §D.1 guard-capacity integrity probe that consumes `derivedGuardCapacity` — belongs to store open/construction, where the SQLite handle exists.

### A.3 Canonical identity — two digests, never one

Canonicalization operates on already-validated policies. Because duplicates were rejected in §A.2, sorting is a pure hashing step: it orders each semantically set-like field lexically **without mutating the registered policy**, so `get()` returns exactly the declared object.

- **Per-class policy digest** — `sha256:<hex>` over that one class's canonical JSON (stable key order throughout, every set-like field sorted). This is the identity of a single condition class's decision semantics.
- **Registry snapshot digest** — `sha256:<hex>` over the canonical JSON of the lexically sorted list of `{ conditionClass, policyDigest }` pairs. This is the identity of the deployed registry as a whole.

The separation is load-bearing: changing or adding an unrelated class changes the snapshot digest while every untouched class keeps its per-class digest byte-for-byte. A registry-only change therefore can never masquerade as a changed class policy, and cannot reset a per-class retry guard or trigger a per-class replay.

The pre-amendment single `policyVersion` (one digest over the whole sorted registry) is superseded and no field named `policy_version` survives anywhere in this design — that name cannot distinguish the two digests, and each consumer below depends on exactly one of them:

| Consumer | Digest used | Defined in |
|---|---|---|
| `evaluation_decisions.policy_digest` | per-class | §B.2 |
| `evaluation_decisions.registry_snapshot_digest` | registry snapshot | §B.2 |
| `transitions.policy_digest` | per-class | §B.4 |
| `notification_intents.policy_digest` | per-class — attribution at decision time, a non-control consumer (R6-04) | §B.3 |
| `evaluation_retry_guard.policy_digest` (key column 4 of 5) | per-class | §D.1 |
| `disabled_condition_classes.faulting_policy_digest` | per-class | §D.3 |
| Replay eligibility trigger | per-class, paired with evaluator version | §D.3 |
| Operator/audit context only | registry snapshot | §B.2 |

### A.4 `production.ts` and registry injection

`PRODUCTION_POLICIES` contains the controller-owned derived classes only — `heartbeat_missing`, `producer_signal_stale`, `producer_clock_skew`, `controller_ingest_unavailable` — plus `evaluator_policy_fault` (§D.2). All five declare `owningProducerDomain: 'controller'` with the empty producer-facing surface rule 7 above requires; 3B wires their derivation. No fixture or test class ships in production; tests inject their own registries.

`evaluator_policy_fault` declares `severity: 'critical'`, `retentionClass: 'extended'`, `recovery.requiredProofClasses: ['policy_replay_verified']`, and `notifyOnTransitions: []`.

`notifyOnTransitions` is empty because the sealed fault path derives its own intent purposes — `controller_diagnostic` when the fault opens, `recovery` when it resolves — and never consults the field (§D.2). Leaving it populated would be dead configuration that appears to control a path it cannot reach.

Its attribute allowlist is the typed shape of the internal fault fact's canonical payload (§D.2):

| Key | `AttributeSpec` |
|---|---|
| `faultingConditionClass` | `{ kind: 'conditionClassRef', allowed: <the complete registered class set> }` (R4-03/R5-01 — §A.2 rule 8 asserts the list's completeness at construction; at fault time the faulting class is registered by definition, so construction guarantees membership) |
| `faultingPolicyDigest` | `{ kind: 'digest', format: 'sha256' }` |
| `faultingEvaluatorVersion` | `{ kind: 'int', min: 0, max: 2147483647, unit: 'version' }` |
| `faultGeneration` | `{ kind: 'int', min: 1, max: 2147483647, unit: 'generation' }` |
| `failureCount` | `{ kind: 'int', min: 0, max: 2147483647, unit: 'failures' }` |

The allowlist is not an ingestion gate for this class — no producer can emit it. It is the registry's self-describing declaration of the fact's shape, and 3A asserts that the internal constructor emits exactly these five keys with values satisfying exactly these specs. That correspondence is what keeps the fault fact typed rather than free-form, and it is why the payload can never carry exception text or a faulting signal's own attributes.

Registry injection: `IncidentStore` gains a required `policies: PolicyRegistry` constructor option (the fleet server passes the production registry; every existing test constructs a fixture registry containing `selfcheck_drift`). Activation is by deploy; git history is the policy audit trail. Policy changes never rewrite historical decisions — every decision and transition keeps the per-class digest that decided it (`policy_reconciled` transitions are Plan 3B+, when a reconciliation pass exists).

## B. Evaluator dispatch, decisions, and intents

`applyLifecycle`'s hardcoded switch becomes policy-dispatched evaluation, following the repo's pure-decision precedent (`decideAuthLossModeEvent`). The store keeps only transactional application; the evaluator keeps only decision semantics.

### B.1 The pure evaluator

New `src/fleet/incidents/evaluator.ts`: `evaluateSignal(input: EvaluationInput): EvaluationDecision` — pure, no clock, no database. All causal guards shipped in PR #2610 (stale-sequence recovery, strictly-fresher supersession, advance-only freshness) move into this function unchanged.

The input carries everything a decision depends on, so the function is total over its arguments:

```text
EvaluationInput {
  envelope;
  producerDomainId;
  policy;
  occurrenceEpisode: EpisodeSnapshot | null;
  openEpisodesOnKey: readonly EpisodeSnapshot[];
  evaluationTime;
}
```

- `producerDomainId` is part of the condition key and of the owning-domain gate's audit trail, so it is an explicit input rather than something the evaluator reads back off the envelope.
- `occurrenceEpisode` is the episode for this exact `(producerDomainId, subject, conditionClass, occurrenceId)`, in whatever state it holds — `null` when none exists.
- `openEpisodesOnKey` is **every** open episode on `(producerDomainId, subject, conditionClass)` in ascending `incident_id`, including the occurrence's own episode when that episode is open. The store does not pre-filter by occurrence id; the evaluator distinguishes occurrences itself, so no correctness rule depends on a SQL predicate outside the pure function.
- The persisted invariant is at most one open episode per occurrence id. Several *different* occurrences may nevertheless be presented, and the evaluator handles that case rather than assuming it away.
- `evaluationTime` is the explicit evaluation time recorded on the decision. The evaluator never calls the wall clock.

The output is an ordered, possibly multi-effect decision:

```text
EvaluationDecision {
  disposition;
  reasonCode;
  severity?;
  effects: readonly EffectSpec[];
  intents: readonly IntentSpec[];
}
```

Each `EffectSpec` names its target as either an existing `incidentId` or a request to open a new episode, together with its projection update and its optional transition `{ from, to, reasonCode }`. In live evaluation the store assigns the incident id when it inserts a newly opened episode and writes that id into the corresponding effect row (R8-03: staged openings never receive an id in their effect row — their realization is recorded in `replay_promotions` at promotion). Effects are applied in array order and become `evaluation_decision_effects` rows with matching `effect_ordinal`, so one decision can emit several supersession transitions plus an onset in a single, ordered, auditable unit. A state-inert decision returns an empty `effects` array.

Each `IntentSpec` names its target effect explicitly and carries only its purpose:

```text
IntentSpec {
  effectOrdinal;   // zero-based index into this decision's effects[]
  purpose;         // 'onset' | 'recovery' | 'controller_diagnostic' in 3A
}
```

**`IntentSpec.effectOrdinal` binds each intent to exactly one of the decision's effects (R3-08).** A decision that supersedes N open episodes and opens one more produces N + 1 effects and, for a policy that flags `opened`, exactly one intent with `effectOrdinal = N` (the opening effect), never one intent per superseded effect. The store derives each intent's persisted `transition_id` and `causing_projection_version` from the transition and projection version that the referenced effect's row produced when it was applied — the `IntentSpec` never names them directly, because they do not exist until the store inserts the effect. An `IntentSpec` whose `effectOrdinal` is out of range, whose referenced effect has no transition (a projection-only effect), or whose `purpose` disagrees with the decision reason (an `onset` on a resolving effect, a `recovery` on an opening one) is a controller-side error, rolls back the accept transaction, and stores nothing.

The store loads this snapshot **inside** the accept transaction and then only applies what the evaluator returned. Reading the snapshot and applying the decision in one transaction is what makes the pure function's view of state authoritative rather than stale.

`EVALUATOR_VERSION` is an integer constant, bumped whenever decision semantics change. It is recorded on every decision and is one half of the replay trigger pair (§D.3).

Heartbeat and notice kinds carry no condition class, so they never reach policy dispatch and produce no decision row (§B.2).

Severity: `incidents.severity` is populated from the policy at `incident_opened`, closing the "NULL until policy registry" placeholder from Plan 1.

Behavioural equivalence obligation: every existing lifecycle, store, and route test passes under dispatch with a fixture registry, with byte-identical receipts.

### B.2 Durable evaluation decisions

Every evaluation invocation **whose accept transaction commits** produces exactly one durable, append-only decision row (R4-08). A deterministic evaluator failure at count 1 or 2 is an invocation with **no** decision: its lifecycle transaction rolls back wholesale, and what it leaves behind is a retry-guard fact (§D.1), not a decision. A decision is per *invocation*, not per transition, because one event can affect several incident projections at once — the store already loops over every open episode on a condition key when a newer occurrence supersedes them.

`evaluation_decisions` (STRICT, append-only — no path updates or deletes a row):

| Column | Notes |
|---|---|
| `decision_id INTEGER PRIMARY KEY AUTOINCREMENT` | |
| `cause_event_id INTEGER` | the causal input in 3A |
| `cause_timer_id INTEGER` | declared-for-3B seam, typed but never populated here |
| `decision_mode TEXT NOT NULL` | `CHECK (decision_mode IN ('live', 'replay', 'internal'))` |
| `condition_class TEXT NOT NULL` | |
| `disposition TEXT NOT NULL` | the same closed set as `events.disposition` |
| `reason_code TEXT NOT NULL` | closed vocabulary, `CHECK`-enforced (below) |
| `policy_digest TEXT NOT NULL` | per-class digest (§A.3) |
| `registry_snapshot_digest TEXT NOT NULL` | audit context only; never a trigger |
| `evaluator_version INTEGER NOT NULL` | |
| `evaluated_at TEXT NOT NULL` | the explicit evaluation time supplied as input |
| `retention_class TEXT NOT NULL` | `CHECK (retention_class IN ('standard', 'extended'))`, copied from the policy for this row's `condition_class` |
| `supersedes_decision_id INTEGER` | set on an appended replay decision; null otherwise |
| `replay_target_epoch INTEGER` | `CHECK ((decision_mode = 'replay') = (replay_target_epoch IS NOT NULL)) AND CHECK (replay_target_epoch IS NULL OR replay_target_epoch >= 1)` (R9-01/R10-02) — the target epoch this replay decision was produced under, immutable |
| `replay_attempt_ordinal INTEGER` | `CHECK ((decision_mode = 'replay') = (replay_attempt_ordinal IS NOT NULL)) AND CHECK (replay_attempt_ordinal IS NULL OR replay_attempt_ordinal >= 1)` (R6-02/R7-04) — the 1-based attempt number this replay decision represents, immutable on the decision itself; each replay chunk transaction binds it as `prior replay_attempt_count + 1 = resulting replay_attempt_count` (code-enforced); a partial `UNIQUE (cause_event_id, replay_attempt_ordinal) WHERE decision_mode = 'replay'` index forbids duplicate ordinals per event (R8-05); and the store-open probe verifies the **dense chain**, not just the latest pointer: for every parked row, its event's replay decisions carry exactly the ordinals 1..`replay_attempt_count` with no gaps, the latest decision's ordinal equals the count, and `latest_replay_decision_id IS NULL ⟺ replay_attempt_count = 0` |

Exactly one causal input is populated. In 3A the constraint is `CHECK (cause_event_id IS NOT NULL AND cause_timer_id IS NULL)`; 3B widens it to an exactly-one-of check when durable timers introduce the second causal source.

**Deferred element (F-07, narrowed by R6-02).** Parent §4's decision-record list includes "safe counters/deadlines". 3A records exactly one decision counter — `replay_attempt_ordinal`, above — because replay decisions genuinely consume it; the remaining counters and every deadline exist only once 3B's absence timers and cadence evaluation do, so those columns arrive with 3B's migration alongside `cause_timer_id`'s widened constraint. The deferral is explicit, not an omission.

`policy_digest` and `retention_class` always describe the policy named by this row's own `condition_class`, which resolves the cases where two policies are in play at once. A parking decision (§D.2 step 2) is a decision about the *faulting* class, so it carries that class's digest and retention class; the internal fault decision that follows it is a decision about `evaluator_policy_fault`, so it carries that policy's digest and `extended` retention. Replay decisions are re-evaluations of the faulting class's own events and therefore carry the faulting class's policy, not the fault policy's.

Prior and resulting state are **normalized**, never packed into the decision row, because a single supersession can conclude several episodes and open one more in the same invocation:

`evaluation_decision_effects` (STRICT), primary key `(decision_id, effect_ordinal)`:

| Column | Notes |
|---|---|
| `decision_id INTEGER NOT NULL` | |
| `effect_ordinal INTEGER NOT NULL` | dense, zero-based, in application order |
| `target_kind TEXT NOT NULL` | `CHECK (target_kind IN ('live', 'provisional_open', 'provisional_ref'))` (R8-03) — the explicit discriminator of the target union below |
| `incident_id INTEGER` | **nullable (R7-01)** — set for effects targeting a live episode; NULL for staged effects on not-yet-promoted episodes (target union below) |
| `provisional_decision_id INTEGER` | with `provisional_effect_ordinal`, names the staged opening effect whose episode this staged effect targets (R7-01); NULL otherwise |
| `provisional_effect_ordinal INTEGER` | see above |
| `prior_state TEXT` | null exactly when the effect opens a new episode |
| `result_state TEXT NOT NULL` | |
| `prior_projection_version INTEGER` | null exactly when the effect opens a new episode |
| `result_projection_version INTEGER NOT NULL` | |
| `transition_id INTEGER` | null when the effect changed a projection without a state transition, such as an `incident_updated` freshness advance — and permanently null on staged replay effects, whose realization is recorded in `replay_promotions` keyed by `(decision_id, effect_ordinal)` (R7-01); `transitions.decision_id` is denormalized convenience |

A state-inert decision has **zero** effect rows. That is the authoritative way to recognise one; the decision row still exists and still carries its reason.

**The staged-effect target union (R7-01, discriminated by R8-03).** Every effect row identifies its target episode in exactly one of three ways, discriminated by the explicit `target_kind` column with a per-kind column-shape CHECK — mutual exclusion alone cannot enforce a three-way union (an all-NULL non-opening row would satisfy it), so each kind pins its exact column shape: (1) `live` requires `incident_id` NOT NULL and the provisional pair NULL — always the case for live-evaluation effects, and for staged effects on episodes that already exist in authority (including episodes promoted by an earlier cohort); (2) `provisional_open` requires `incident_id` and the provisional pair all NULL **and** both prior fields NULL (`prior_state` and `prior_projection_version` — their nullity always agrees, CHECK-enforced; R9-03), is writable only by replay staging, and carries opening-state semantics — the row *is* the durable provisional handle, identified by its own `(decision_id, effect_ordinal)`, and the episode's `incident_id` comes into existence only at promotion, recorded in `replay_promotions`; (3) `provisional_ref` requires the provisional pair NOT NULL, `incident_id` NULL, **and both prior fields NOT NULL** (existing-episode semantics — a reference to a staged-open episode always has a prior state and version; R9-03), naming an opening effect. **Repeated references chain (R9-03, made deterministic and state-consistent by R10-03):** multiple effects may reference one opening across chunks; their total order is exactly `(cause_event_id, decision_id, effect_ordinal)` — the effect-ordinal tie-breaker covers multiple effects of one event's decision — and the probe validates **both continuities**: each reference's `prior_projection_version` equals the previous effect's `result_projection_version` **and** its `prior_state` equals the previous effect's `result_state`, for that provisional episode, starting from the opening's result. The chain restarts at each provisional opening and at each target epoch (R9-01): a predecessor from another epoch is a probe failure, never a chain link. **Referential validity is transactional and probed (R8-03):** the chunk transaction that writes a `provisional_ref` verifies its pair resolves to an earlier `provisional_open` effect of the same class, same generation, and same **replay-target epoch** (R9-01 — pair equality alone would accept an opening from an abandoned incarnation of a reverted pair), **and that the named opening is not yet realized — it has no `replay_promotions` row (R11-01):** once an opening has been promoted its episode exists in live authority, and any newly staged effect against that episode must be `target_kind = 'live'` with the realized `incident_id`. The store-open probe re-verifies every `provisional_ref` the same way, additionally requiring that a `provisional_ref` whose named opening carries a `replay_promotions` row carries one itself — both realized, a completed cohort's internal references — with the single exception of the in-flight resumable state where the generation is `promoting` and the referencing effect lies above `promotion_cursor_event_id` inside the fenced cohort (R11-01) — and, inside that exception, the referenced opening must itself belong to the **same active cohort (R15-01)**: either not yet realized (no `replay_promotions` row — a later chunk of this cohort will realize it) or realized by an earlier chunk of this same cohort (its mapping carries the current `promotion_cohort_ordinal`); an opening whose mapping carries an earlier cohort's ordinal fails the probe even inside the exception. Dangling, cross-epoch, cross-target, cross-generation, cross-cohort, and stale-provisional references are therefore unrepresentable in accepted state. The overlay orders `openEpisodesOnKey` deterministically across restart: live episodes ascending `incident_id`, then provisional episodes ascending their opening event's `event_id` — both rebuildable from durable staged rows alone.

**Staged live effects chain from authority (R12-01), as an active segment (R13-01).** Provisional chains are not the only ordered staging: a target may stage multiple `live`-target effects against one episode — an episode that predates the fault, or one realized by an earlier promotion cohort. What chains is never a timeless per-tuple history but the **active staged-live chain segment** for `(condition_class, fault_generation, policy_digest, evaluator_version, replay_target_epoch, incident_id)` — the operational target key plus the episode: exactly the live-target effects reached through the same membership rule the overlay uses (R11-01) — a `parked_evaluations` row of the active class and generation with `state = 'resolved'`, owning the effect's decision as its `latest_replay_decision_id`, stamped with the complete active target tuple — and, while the generation is `promoting`, inside the current fenced cohort. Promoted prefixes, `pending` rows, superseded decisions, and abandoned epochs' effects are outside the segment: a promoted effect's correctness is witnessed by `replay_promotions` and the durable transition and projection history it created, never by holding its original prior fields up to today's projection, and an abandoned target's tail can never serve as a later target's predecessor. Within the segment, effects are totally ordered by the same `(cause_event_id, decision_id, effect_ordinal)` order. The segment's first effect's `prior_state` and `prior_projection_version` must equal the episode's **current authoritative projection** — which already incorporates every promoted prefix, and is well-defined because an ingestion-disabled class's projections stay frozen (R6-01) — and every subsequent effect must continue its predecessor on both fields: its `prior_state` must equal the predecessor's `result_state`, and its `prior_projection_version` must equal the predecessor's `result_projection_version`. The chunk transaction that stages a live effect validates its link against the durable segment, and the store-open probe reconstructs every **active** staged-live segment the same way — historical effects are never re-anchored to current authority: a promoted effect is validated through its `replay_promotions` mapping, while an abandoned effect's expected integrity state is the **absence** of any `replay_promotions` row (R14-03 — absence is the verified invariant there, not a validation gap); a first effect that does not bind to authority, or a successor that does not continue its predecessor, is a probe failure. This holds whatever state the episode is in — including an episode **closed by an earlier promoted verdict**: any later staged effect against it still chains from that closed projection, never from a fabricated or stale prior.

**Persisted staged intent specs (R7-01).** For staged replay decisions, the evaluator's `IntentSpec`s are persisted at staging time into append-only `evaluation_decision_intent_specs` (STRICT): primary key `(decision_id, intent_ordinal)`, `effect_ordinal INTEGER NOT NULL`, `purpose TEXT NOT NULL` with the closed purpose CHECK. Promotion consumes **these exact specs** — it never re-derives intent semantics from the policy, so no second copy of evaluator logic exists in the store. Live decisions realize their intents immediately and persist no spec rows.

**The promotion mapping (R7-01).** Append-only `replay_promotions` (STRICT): primary key `(decision_id, effect_ordinal)`, `incident_id INTEGER NOT NULL` (the realized episode), `transition_id INTEGER` (NULL for projection-only effects), `promotion_cohort_ordinal INTEGER NOT NULL` (R15-01 — the identity of the fence whose promotion wrote the row, stamped at creation, immutable), `promoted_at TEXT NOT NULL`. Written only by promotion chunks, it is the authoritative record of which incident and which transition realized each staged effect — including the multi-effect case R3-08's `effectOrdinal` binding depends on — and its primary key doubles as the promotion idempotence witness across crash-resume. **Every fence has a durable cohort identity (R15-01):** the generation row's `promotion_cohort_ordinal` is null until the first fence and incremented by one in each fence transaction — monotonic across the generation's whole history, epochs included — and every `replay_promotions` row is stamped with the cohort ordinal whose promotion created it. A committed mapping may satisfy a `provisional_ref` only when it carries the **current** cohort ordinal — written by an earlier chunk of the same active cohort; a mapping stamped with any earlier cohort's ordinal marks an episode that was already live authority when the current cohort was staged, so a `provisional_ref` reaching it is corruption — the staged effect must have been `live` (R13-01) — and both promotion and the store-open probe fail closed on it. **The mapping is probed row-by-row at store open (R15-02).** `replay_promotions` carries no SQL foreign keys, so its integrity is code-owned and verified for **every** row: (1) the `(decision_id, effect_ordinal)` staged effect exists and its decision is `decision_mode = 'replay'` with a valid staged target shape; (2) the `incident_id` names an existing incident; (3) a non-null `transition_id` names an existing transition that belongs to that same incident and carries that same `decision_id`, and is non-null exactly when the staged effect implied a state transition; (4) the mapping is attached to promoted work — its decision's cause event has a `parked_evaluations` row that is terminal `promoted`, or lies at or below `promotion_cursor_event_id` of the currently `promoting` cohort with the current cohort ordinal — a mapping attached to abandoned or otherwise non-promoted work is corruption; and (5) the row's cohort ordinal lies between 1 and its generation's current `promotion_cohort_ordinal`. Any violation fails closed per the R4-07 degradation contract.

`evaluation_decision_intents` (STRICT), primary key `(decision_id, intent_ordinal)` with `UNIQUE (intent_id)`: `decision_id`, `intent_id`, `intent_ordinal`. One decision may create several ordered intents across several projection effects. No JSON array of foreign keys is authoritative anywhere in this design.

`events` gains `initial_decision_id INTEGER`, pointing only at the decision that produced the original receipt.

**What immutability means here.** `acceptSignal` already back-fills `events.disposition`, `incident_id`, and `transition_id` after the row is inserted, inside the same accept transaction; `initial_decision_id` joins exactly that set of in-transaction back-fills. Immutability is therefore a **post-commit** property: once the accept transaction commits, no path updates or deletes an `events` row. Policy replay appends new decision, effect, transition, and intent rows and never changes the committed event, its disposition, its `initial_decision_id`, its original decision, or the receipt already returned to the producer.

An exact-byte replay is answered at §C gate 5 from stored rows, ahead of every schema and policy gate: it returns the original receipt and creates **no** decision, even when the stored envelope would no longer pass the current schema, scope, or policy.

**Closed reason vocabulary**, `CHECK`-enforced on `evaluation_decisions.reason_code`:

`condition_observed`, `observation_advanced`, `newer_occurrence`, `verified_recovery`, `no_open_episode`, `stale_observation`, `stale_recovery`, `recovery_proof_insufficient`, `quarantined_future_skew`, `parked_evaluation_faulted`, `retry_guard_capacity_exceeded`, `replay_state_inert`, `policy_replay_verified`, `replay_attempt_failed` (R5-03).

Two relationships this vocabulary must not be read as implying:

- **Decision reasons and transition reasons are separate columns.** `transitions.reason_code` keeps its v1 shape — `TEXT NOT NULL`, no `CHECK` — because adding one would force a second table rebuild for no behavioural gain. The closed vocabulary above constrains the new `evaluation_decisions.reason_code` only. A decision's reason names the invocation's primary outcome; each effect's transition keeps its own reason. They deliberately differ for multi-effect decisions: a new occurrence that supersedes two open episodes and opens a third is one decision with reason `condition_observed` and three effects whose transitions read `newer_occurrence`, `newer_occurrence`, and `condition_observed`. The three reason codes live code already writes (`condition_observed`, `newer_occurrence`, `verified_recovery`) are unchanged and remain valid transition reasons.
- **`policy_replay_verified` is deliberately one token in two vocabularies.** It is the `recoveryProofClass` the `evaluator_policy_fault` policy requires (§A.4) *and* the decision reason on the replay-recovery decision (§D.3). One fact — a drained class re-evaluated cleanly — is named identically in the envelope vocabulary and the decision vocabulary. The two are validated independently and neither derives from the other.

**Which events get a decision row.** Every accepted condition event gets exactly one, including quarantined, stale, proof-insufficient, disabled-class-parked, and replay evaluations. Rejected signals (§C gates 6–11) get none, because they store nothing at all. Heartbeat and notice records get none, because they bypass evaluation entirely.

### B.3 Notification intents

`notification_intents` (STRICT) records the intent to notify. Nothing in 3A reads it — Plan 5 owns delivery — but the row must already carry enough immutable identity for a future worker to judge whether the intent still describes current state, without re-deriving that judgement from mutable projections.

| `occurrence_id TEXT NOT NULL` | which occurrence of the condition this is about |

**Relevance is judged by occurrence and projection version, never by digest equality (R6-04).** `notification_intents.policy_digest` is attribution — the per-class digest current when the decision was made — not a liveness predicate: Plan 5 must never compare it against the current registry to decide staleness, so an existing intent (including an `evaluator_policy_fault` diagnostic) never becomes stale solely because a registry change altered its class's digest. `occurrence_id` and `causing_projection_version` are what make the intent's relevance immutable. A transition alone does not say which occurrence it concluded or what the projection looked like when the decision was made, so without them a delivery worker could only re-read the current projection — by which time the incident may have been superseded, resolved, and reopened. The recorded pair lets Plan 5 decide staleness by comparison rather than by guesswork.

The `UNIQUE (transition_id, purpose)` constraint makes duplicate creation impossible at the schema level: one transition yields at most one intent per purpose, so a retried or replayed evaluation cannot manufacture a second notification for the same fact.

3A emits only `onset`, `recovery`, and `controller_diagnostic`. `escalation` and `reminder` are declared-for-3B members of the closed purpose set, typed but never written here — renotification schedules and severity escalation are 3B scope.

`onset` and `recovery` come from the policy's `notifyOnTransitions` flags `opened` and `resolved` (§A.1). `controller_diagnostic` is emitted only by the sealed fault path (§D.2). Supersession transitions produce no intent in 3A.

Each intent links to the decision that created it through `evaluation_decision_intents` (§B.2). One decision may create several ordered intents across several projection effects, and `intent_ordinal` preserves that order.

### B.4 Migration v3

One numbered migration carries the whole 3A schema. It runs inside the existing per-migration `BEGIN IMMEDIATE` / `COMMIT` wrapper in `src/fleet/incidents/db.ts`, which rolls back on any error.

- **`events` table rebuild.** SQLite cannot alter a `CHECK` constraint, so v3 rebuilds `events` to widen the disposition check with the ninth value `stored_evaluation_faulted` and to add `initial_decision_id INTEGER`. All rows are copied; the `sqlite_sequence` AUTOINCREMENT identity is preserved so post-migration event ids can never collide with historical ones; and **every existing constraint and index is recreated verbatim — explicitly including `UNIQUE (producer_id, signal_id)`** (F-02), on which gate-7 byte-idempotency and the parent §3 replay contract depend. This is an approved wire-contract change — unlike the ad-hoc disposition rejected in the 2026-07-29 audit remediation — and it is why 3A lands as a numbered migration.
- **Referential integrity is code-enforced (F-09).** The nine new tables reference each other and the existing tables by id, but declare no SQL `FOREIGN KEY` constraints — consistent with the v1/v2 tables. Integrity is enforced inside the store's transactions (every reference is written in the same transaction as its referent), and the §E migration/replay suites assert it.
- **`transitions`** gains `policy_digest TEXT` and `evaluator_version INTEGER`, both nullable for pre-v3 rows and both enforced NOT NULL in code for new rows, plus `decision_id INTEGER` (nullable) — set on promotion-created transitions to link back to the staged replay decision they realize (R6-01); denormalized convenience, with `replay_promotions` as the authoritative per-effect mapping (R7-01). These are denormalized for query convenience; the decision and effect rows are authoritative.
- **New tables**, each defined once in the section that owns its behaviour: `evaluation_decisions`, `evaluation_decision_effects`, `evaluation_decision_intents`, `evaluation_decision_intent_specs`, `replay_promotions` (§B.2); `notification_intents` (§B.3); `evaluation_retry_guard` (§D.1); `parked_evaluations` and `disabled_condition_classes` (§D.3).
- **Indexes** supporting the replay drain and audit reads: `evaluation_decisions (cause_event_id)`, `evaluation_decision_effects (incident_id)`, `parked_evaluations (condition_class, state, event_id)`, `events (condition_class, event_id)`, and `evaluation_retry_guard (condition_class, policy_digest, evaluator_version)` for active-pair counting (R6-01 follow-through of the round-5 review's implementation note).

## C. Ingestion enforcement — fail-closed order

### C.1 The enforcement order

Every signal traverses the gates below in this exact order. Gates 1–4 are unchanged Plan 2 behaviour in `src/fleet/routes/signals.ts`; gates 5–12 run inside `IncidentStore.acceptSignal`. Each gate is evaluated only if every earlier gate passed, so the first failure determines the response and no later gate can widen it.

**Identity answering precedes all validation, and this relocates two Plan 2 gates.** The route as shipped parses the envelope schema and applies the producer scope allowlists *before* it calls `acceptSignal`, while the store answers replays and identity conflicts *before* its own validation. A signal accepted under an earlier schema or an earlier scope grant therefore could not replay: the route rejected it with 422 or 403 and never reached the stored row holding its receipt, so tightening a schema or revoking a scope retroactively destroyed the idempotency of signals already accepted. 3A resolves this by making the store's pipeline the single validation authority. The route stops duplicating schema and scope validation ahead of the replay check and delegates both to `acceptSignal`, which runs them after the identity short-circuit. This is a **declared amendment to Plan 2's route ordering**, not an incidental edit: the gate set, every failure response, and every static message are unchanged — only the position of the identity short-circuit relative to the schema and scope gates moves.

Producer scope moves with the schema gate for a structural reason rather than by association: scope authorization reads `kind`, `conditionClass`, and `subject` off the *parsed* envelope, so it can never precede schema validation. Once schema validation moves behind the identity short-circuit, scope necessarily follows it. The store receives the authenticated producer's scope allowlists on its existing producer-context argument rather than a `ProducerStore` handle, so the store gains no dependency on the producer module and tests keep constructing the context directly.

Gates 6 through 11 are rejections and store **zero rows** — no event, decision, transition, intent, or retry-guard row — matching the byte-contract precedent that a rejected signal leaves no trace. Gate 12 is not a rejection: a proofless recovery is well-formed and truthful, so it is accepted and stored while remaining state-inert.

Gate-by-gate detail:

- **Gate 4 — exact-byte decode and parse.** Unchanged. The route keeps its own strict-UTF-8 decode and `JSON.parse` for the 400, and the store repeats both on the bytes it receives. The duplication is deliberate and cannot reorder anything: a body that fails to decode or parse has no extractable `signalId`, so it could never have been answered as a replay, and rejecting it at the route pre-empts no identity short-circuit that could have fired.
- **Gate 5 — identity short-circuit.** The store extracts `signalId` from the parsed body and looks up `(producer_id, signal_id)`. A stored identity is answered as an idempotent replay when the payload digest matches the exact request bytes, and as a 409 identity conflict when it does not. Because this now precedes gates 6 through 12, a signal stored before a schema tightening, a scope revocation, or a policy change still replays its original receipt byte-for-byte, and a conflicting resend still surfaces as a conflict rather than as an invalid or unauthorized signal (§C.2). The lookup is keyed by the authenticated producer's own id, so a producer can only ever short-circuit onto its own stored rows — answering a replay after a scope revocation returns that producer nothing it was not already given, and stores nothing new.
- **Gate 6 — envelope schema.** Unchanged in content, including the heartbeat/notice attribute prohibition below; only its position moves behind gate 5.
- **Gate 7 — producer scope allowlists.** Unchanged in content: the authenticated producer's kind, condition-class, and subject allowlists must admit the envelope, and a denial returns the existing 403 with its existing static message, `signal is outside the producer scope`. Only its position moves behind gate 5. A scope revocation therefore stops every new signal while leaving intact the receipt for a signal the producer already stored.
- **Gate 8 — policy lookup.** A `condition_observed` or `condition_recovered` envelope whose `conditionClass` is absent from the active registry is rejected. The route maps it to **422 `{ code: 'condition_class_unknown', retryable: false }`** — the only new error code (parent §4 names it; §3's closed taxonomy is amended accordingly).
- **Gate 9 — owning-domain gate.** The store requires `authenticatedProducer.producerDomainId === policy.owningProducerDomain`. A mismatch returns the existing **403 `condition_class_not_allowed`** response with its existing static message, `signal is outside the producer scope`. Reusing gate 7's code and message is deliberate: a producer that is correctly scoped for the kind, class, and subject but belongs to a foreign domain must not receive a response that distinguishes it from an ordinary scope denial, because that difference would be an oracle for which classes exist and which domain owns them. Negative tests cover both `condition_observed` and `condition_recovered` from such an otherwise-correctly-scoped producer.
- **Gate 10 — kind and subject versus policy.** The policy's `permittedKinds` and `permittedSubjects` must admit the envelope. This is defence in depth behind gate 7's producer scoping: the producer registry and the policy registry are independently administered, and neither is trusted to imply the other.
- **Gate 11 — attribute semantics.** Every attribute key present on the envelope must exist in the policy's `attributeAllowlist`, and its value must satisfy that key's `AttributeSpec` exactly (§A.1). There is no stripping, coercion, or partial acceptance: a single unknown key or ill-typed value rejects the whole signal and stores nothing. Absent optional attributes are not synthesised.
- **Gate 12 — recovery proof.** A `condition_recovered` envelope for a policy with a non-empty `recovery.requiredProofClasses` must carry a `recoveryProofClass` drawn from that set. Without one the event is accepted and stored with disposition `stored_no_state_change` — no new disposition value — and its decision row carries reason `recovery_proof_insufficient` (§B.2), which is what distinguishes it from an ordinary no-op.

### C.2 Decision-creation matrix

The gate order above decides what is *stored*; this matrix decides what is *recorded*. Two rules govern it, and every row below is an instance of them:

1. **A rejection stores zero rows.** Gates 1 through 11 store no event, no decision, no effect, no transition, no intent, and no retry-guard row. There is no partial write and nothing to roll back, because nothing is written before the last rejecting gate has passed.
2. **Every accepted condition evaluation stores exactly one decision.** Not one per transition and not one per affected incident — one per invocation, with its effects normalized (§B.2).
3. **A deterministic evaluator failure is not a gate rejection.** It occurs strictly *after* all twelve gates have passed. The lifecycle transaction rolls back (so it stores no event, decision, effect, transition, or intent) and is then followed by a separate transaction that upserts one `evaluation_retry_guard` row (§D.1) — the guard row is the sole storage side effect of failures 1 and 2. On the third failure the parking transaction (§D.2 shape 1) adds an event and decision row and the response becomes 201. This is why the retry-guard row appears in rule 1's "zero rows on rejection" list yet the R3-09 failure-1/2 matrix rows do write one: they are not rejections.

| Final zero-pending replay recovery fact (§D.3) | not an HTTP path | one | one | `internal` | `policy_replay_verified` | 1 | `recovery` |

**Dispositions for the accepted rows.** Every accepted row above stores its event with the disposition its outcome implies, and the decision row carries the same value (§B.2): `heartbeat_recorded` and `notice_recorded` for those two kinds **within the skew bound**; `stored_quarantined_observation` for **any kind** beyond the future-skew bound — a future-skewed heartbeat or notice quarantines exactly like a condition signal (F-05: matching the shipped store behavior and parent §3), it merely creates no decision row because bypassed kinds are never evaluated; `incident_opened` for a new occurrence, whether or not it supersedes others; `incident_updated` for a sequence advance on the same occurrence; `incident_resolved` for a verified recovery; `stored_stale_observation` for the three stale cases; `stored_no_state_change` for a concluded episode, an absent episode, and an insufficient recovery proof; and `stored_evaluation_faulted` for both parked rows — a disabled class and a retry-guard ceiling. `stored_evaluation_faulted` is the ninth disposition value, reachable only after the v3 rebuild widens the `events` CHECK (§B.4).

Replay is the one case where the event's disposition and its decision's disposition differ. The parked event keeps `stored_evaluation_faulted` permanently, because a committed event is immutable; the appended replay decision carries the disposition the re-evaluation actually produced. Reading the current outcome of a replayed event therefore means reading its latest decision, never its event row.

Every appended replay decision sets `supersedes_decision_id` to the decision it re-evaluates and leaves that earlier decision, the event, its disposition, and the returned receipt untouched.

### C.3 Rejection transport

`AcceptResult`'s `invalid` variant carries a closed `policyRejection` field so the route maps store-internal gates exhaustively without inspecting messages:

```text
policyRejection?:
  | 'kind_not_allowed'            // gate 7
  | 'subject_not_allowed'         // gate 7
  | 'condition_class_not_allowed' // gate 7 and gate 9
  | 'condition_class_unknown'     // gate 8
  | 'invalid_signal'              // gates 6, 10, and 11
```

The route maps `kind_not_allowed`, `subject_not_allowed`, and `condition_class_not_allowed` to 403 with that code and the existing static scope message, `condition_class_unknown` to 422 `condition_class_unknown`, and `invalid_signal` to the existing 422 `invalid_signal`. When the field is absent the existing Plan 2 mapping is unchanged (`malformedJson` selects 400 `malformed_request`, otherwise 422 `invalid_signal`). This closed field replaces the ad-hoc `unknownConditionClass: true` boolean of the pre-amendment draft, which could not express a 403 outcome; the shipped `malformedJson` field is unchanged.

The three scope codes join this field because gate 7 now executes inside the store (§C.1). The route no longer computes a denial itself, so it must be able to reproduce the exact code and status the shipped 403 path produced — hence the codes travel in the closed field rather than being re-derived. `condition_class_not_allowed` is deliberately reachable from both gate 7 and gate 9 and carries the same status, code, and message from either, preserving the §C.1 gate-9 rule that a foreign-domain producer must be indistinguishable from an ordinarily out-of-scope one.

### C.4 Heartbeat and notice envelopes prohibit attributes

In 3A a `heartbeat_observed` or `notice_recorded` envelope must not carry the `attributes` member at all, including `{}`. These kinds have no condition class, therefore no policy, therefore no allowlist against which attributes could be validated; accepting unvalidated metadata on them would be the one hole in gate 11. Typed stream metadata arrives in 3B with the heartbeat registry that gives it a schema.

This is an envelope-schema change, not a store-side check: `attributes` moves out of `commonFields` into the two condition variants only. Because all four variants are already `.strict()`, an `attributes` member on a heartbeat or notice fails schema parsing, so the rejection surfaces at gate 6 as the existing 422 `invalid_signal` — no new code, no new error value.

Two existing byte fixtures reference `attributes` on a `heartbeat_observed` envelope, and they are affected differently:

- The `€` byte-stability fixture (`euroHeartbeatBytes` in `tests/fleet/routes/signals.test.ts`) is currently **accepted**, and it must keep the property it exists to prove: that a body split inside a multibyte code point is digested over the original bytes. It moves to a `condition_observed` envelope under a fixture policy and carries **no** `attributes` member, with the `€` relocated into its `signalId` — an envelope identity field, which §A.1 explicitly leaves on the shipped wire grammar. The `€` cannot remain in an attribute value: no `AttributeSpec` kind accepts it — it is not an enum member, not an integer or boolean, not a digest, and not a registered condition class (R4-03). It cannot move to `subject` either, because `permittedSubjects` is registry-side and therefore safe-identifier-constrained, so a `€` subject could never match a policy at gate 10. An identity field is the only place in the envelope where a multibyte code point both survives the tightening and still exercises the chunk split.
- The two invalid-UTF-8 fixtures (`hb-ff` in `tests/fleet/routes/signals.test.ts` and `tests/fleet/incidents/store-accept.test.ts`) are decided at gate 4 by the strict decoder, before any schema parse. Their outcome — 400 `malformed_request` and `malformedJson: true` respectively — is unchanged, and they may keep their heartbeat shape.

### C.5 The `controller` producer domain is reserved

External registration of a producer in domain `controller` is rejected: `ProducerStore.register()` returns its existing `{ ok: false, reason: 'invalid_input' }`, which the admin route surfaces as the existing 422 `invalid_registration`. No new store reason and no new wire code are introduced.

Controller-owned facts never pass through producer enrollment or credentials. They are written through an internal-only store entry point with a reserved identity (§D.2) that **bypasses** the producer-facing gates rather than satisfying them.

Gate 9 is what makes producer emission of a controller-owned class impossible: no producer can hold domain `controller`, so no authenticated producer request can ever equal such a class's `owningProducerDomain`. The internal path is not an exception to that gate — it is not a producer request at all. Replacement and adoption authority for controller-derived classes remains an explicit 3B policy and never weakens this gate.

## D. Evaluator faults, parking, and replay

### D.1 The retry guard

`evaluation_retry_guard` (STRICT) mechanizes the locked §4 poison-signal guard. Its key is **derived from** the five-part key parent §4 names, substituting the per-class policy digest for the parent's `policyVersion` — under §A.3 the digest *is* the policy's version identity, so the substitution preserves the parent's intent while making the reset semantics precise.

| Column | Notes |
|---|---|
| `producer_id TEXT NOT NULL` | key column 1 of 5 |
| `signal_id TEXT NOT NULL` | key column 2 of 5 |
| `payload_digest TEXT NOT NULL` | key column 3 of 5 |
| `policy_digest TEXT NOT NULL` | key column 4 of 5 — the **per-class** digest (§A.3) |
| `evaluator_version INTEGER NOT NULL` | key column 5 of 5 |
| `condition_class TEXT NOT NULL` | recorded from the envelope at failure time; **not** a key column |
| `failure_count INTEGER NOT NULL` | `CHECK (failure_count BETWEEN 1 AND 3)` (R5-04) — 1 and 2 are standalone-recorded failures; 3 exists only in rows written by the shape-1 threshold transaction; no fourth identical failure is reachable (the class is disabled) |
| `first_failed_at TEXT NOT NULL` | |
| `last_failed_at TEXT NOT NULL` | |

`PRIMARY KEY (producer_id, signal_id, payload_digest, policy_digest, evaluator_version)` (F-06: every new table declares its primary key).

The fourth key column is the **per-class** digest (§A.3), not the registry snapshot digest. If it were the snapshot, editing any unrelated class would change the key, silently reset every accumulated `failure_count`, and let a genuinely poisonous signal retry indefinitely. Only a change to the faulting class's own policy resets its guard.

**Why `condition_class` is stored rather than joined (R3-03).** The per-class ceiling below, the §F derived global bound, and the store-open integrity probe (R4-01) all count or group guard rows *per condition class*. A deterministic failure at count 1 or 2 stores **no event row** — the lifecycle transaction rolled back — so there is nothing to join against: `events` cannot supply the class for precisely the rows the ceiling has to count. Recording it on the guard row at failure time is what makes the ceiling computable at all. It sits deliberately outside the primary key: the class is functionally determined by `payload_digest` (identical bytes carry an identical `conditionClass`), so keying on it would widen the key without distinguishing any two rows while disturbing the reset semantics the five-part key exists to define.

Guard writes for failures **1 and 2** are each their **own transaction after** the lifecycle transaction has rolled back — same handle, strictly sequential. The guard write is never part of the transaction it is recording the failure of, because that transaction is precisely the one being discarded.

A deterministic evaluation failure rolls back the lifecycle transaction, then upserts the guard row, incrementing `failure_count` when all five key columns match exactly: same producer, same signal id, same bytes, same class policy, same evaluator. Any difference is a different key and starts at one.

**The third identical failure parks atomically — the guard write joins the parking transaction (R4-01).** When the upsert would take `failure_count` from 2 to 3, the store does not run it standalone. Instead the guard update becomes the first write of the §D.2 shape-1 parking transaction, which runs immediately after the failed lifecycle transaction rolls back — *while the request's exact bytes and parsed envelope are still in hand*. Either the guard reaches 3 **and** the event is parked, the class disabled, and the fault fact emitted, or none of that happens: a crash anywhere inside the combined transaction rolls the guard back to 2, the producer's request fails without a receipt, and the producer's retry re-runs evaluation and re-attempts the same combined transaction. The same rule applies to the guard insertion that reaches the per-class ceiling: it joins the capacity-cause parking transaction rather than committing separately.

This atomicity is what closes the crash boundary the guard/parking split would otherwise open. There is **no store-open "owed parking" completion** — a payload digest is irreversible, and no persisted guard state could reconstruct the original event bytes, envelope, or receipt after the fact. The round-3 owed-parking recovery clause is superseded by this construction: the crash window it tried to repair no longer exists. What remains at store open is an **integrity probe over the full reachable guard projection (R4-01/R5-04)**, checked per registered class: (a) no guard row with `failure_count = 3` may lack a corresponding `parked_evaluations` row; (b) the active-pair row count must not exceed 256; (c) an active-pair count of exactly 256 must be accompanied by a `disabled` generation for the class with `disabled_reason` `retry_guard_capacity_exceeded` and its cause-bound parking decision — the saturated state of 256 sub-threshold rows with **no** parked or disabled row is unreachable (the 256th insertion can only exist inside a committed capacity parking transaction) and is explicitly corrupt; (d) every `parked_evaluations` row references an existing event whose `condition_class` matches. Locally enforceable constraints live in SQLite `CHECK`s (the `failure_count` range above); cross-table predicates live in this probe. Any probe failure indicates storage corruption, is classified as a core controller/storage failure, and fail-closes incident ingestion (R4-07) — never repaired by synthesis.

**Capacity is bounded in 3A, not deferred (H-03).** Guard rows are not bounded by the parked-event count: every distinct authenticated signal that fails deterministically leaves a guard row whether or not it ever reaches three failures, so unique failing signals could otherwise grow the database without limit.

- **Age pruning.** Rows older than 30 days that have **no** corresponding `parked_evaluations` record are pruned at store open, and again immediately before any guard insertion that would otherwise cross a ceiling. A row with parked work is never pruned at any age — the parked event is the evidence, and pruning its guard row would discard the record of why it was parked.
- **Active-pair scoping with retention-based continuation (R5-02, corrected by R6-03).** The enforcement ceiling counts only a class's **active-pair rows** — rows whose `(policy_digest, evaluator_version)` equals the class's current per-class digest and current `EVALUATOR_VERSION`. Rows carrying a stale pair are **historical**: they stop contributing to capacity the moment the pair changes — by pair scoping alone, with no separate retirement mechanism — so a repaired policy starts with a clean enforcement budget instead of inheriting up to 255 rows of old-pair pressure that would let its first failure immediately re-disable it. **Historical rows are retained, not deleted (R6-03) — under a deterministic cardinality bound (R7-03):** the rows themselves are the durable audit of those failures and the continuation state for a pair revert. Retention per class is bounded by **4 distinct stale pairs and 1,024 rows, counted over evictable rows only (R8-04)** — a row pinned by parked work is evidence, never counts toward either bound, and is never touched by compaction (its volume is bounded by the parked backlog). When admitting a newly staled pair would exceed the bound, compaction runs **in the same transaction**: it removes **all evictable rows of the oldest historical pair**, where a pair's age is `MAX(last_failed_at)` over its rows and ties break lexicographically on `(policy_digest, evaluator_version)` — fully deterministic, always freeing a pair slot (a pair whose evictable rows are gone no longer counts toward the pair bound, even if pinned rows remain). Reconciliation — recomputing which pairs count and compacting if needed — runs at store construction and again before the first guard insertion under a changed pair, in one transaction each. The 30-day age pruning above remains the secondary, time-based bound. A pair evicted by compaction behaves on revert exactly like one aged past 30 days: its identities restart at count 1, which is the stated boundary of continuation. A pair revert **while the pair remains retained** therefore finds its exact five-part-key history intact — an identity at `failure_count = 2` under D1, after D1 → D2 → D1, parks on its very next failure at 3 — which is also what bounds policy-toggle churn inside the retention window. Continuation is a property of retention, not a guarantee against it (R9-04): a pair may leave retention before 30 days **solely** through the declared cardinality compaction below, and beyond 30 days the age pruning is the deliberate, stated boundary; a pair evicted by either mechanism restarts at count 1 on revert. Rows for unregistered classes follow R3-10 (excluded from enforcement, removed only by age pruning). **Transactional binding:** the active-pair count, the five-part key-existence check, and the selected write — normal insert, threshold parking, or capacity parking — are evaluated and applied inside one SQLite write transaction, so no concurrent request can interleave between the count and the write it selects.
- **Ceilings.** The **per-class ceiling of 256 active-pair guard rows (R5-02) is the enforcement boundary and the isolation mechanism**: it is evaluated against the triggering event's own condition class only, so one class's guard growth can never disable a different, healthy class (which would contradict §D.2's class-isolation guarantee and sidestep parent §4's three-failure precondition). The global figure is **derived, not enforced as a disable trigger**: total guard capacity is `256 × <currently registered class count>`, counted over active-pair rows (R5-02). **Computation and verification live in different places (R4-07):** `buildPolicyRegistry` computes the figure — pure arithmetic over its policy inputs, no database access — and exposes it on the registry; the **data-dependent integrity probe** that compares actual guard-row counts against it (and detects a per-class count above 256) runs at store open and store construction, where both the registry and the SQLite handle exist. A probe failure fail-closes **incident ingestion only** — incident routes degrade to 503 exactly as a failed startup probe does under Plan 2's DB-ownership contract — and never takes down the rest of the fleet process. **The derived bound counts guard rows for currently registered classes only (R3-10).** When a class is removed from the registry, its `evaluation_retry_guard`, `parked_evaluations`, and `disabled_condition_classes` rows are preserved (the audit trail cannot silently discard fault history), but the derived global assertion excludes them — otherwise a legitimate registry contraction would trip the bound and be misreported as storage corruption. Parked work for an unregistered class stays disabled by construction: replay eligibility (§D.3) requires an active current class digest and evaluator version, and neither exists for a class the registry no longer knows. Such work continues to be surfaced through its already-open `evaluator_policy_fault` incident, not through the derived-bound alarm. While the per-class ceiling holds *for every currently registered class*, the derived global bound over registered-class rows cannot be crossed by well-behaved operation; observing it crossed at runtime therefore indicates a storage or bookkeeping integrity anomaly on a live class and is classified as a core controller/storage failure (parent §4's global fail-closed category), never as grounds to disable an unrelated class.
- **Overflow parks, it never drops — with exact pre/postconditions (R4-04).** For a class with **active-pair** guard-row count `c` (R5-02): while `c < 255`, a new-key failure inserts its guard row normally; the insertion that would make `c = 256` instead runs the §D.2 shape-1 parking transaction with the **capacity** cause — the guard insertion joins that transaction (R4-01), the triggering event is parked, and the class is disabled with `disabled_reason` `retry_guard_capacity_exceeded` and decision reason `retry_guard_capacity_exceeded`, opening or updating the evaluator-fault incident. Overflow is treated as a fault to be reported, never as a reason to discard a signal or a failure record. A **persisted** state with `c > 256` for any currently registered class is a corrupt postcondition — unreachable through either path above — detected by the store-open integrity probe and classified as a core controller/storage failure; the ordinary ceiling-reaching insertion is never so classified, and a corrupt count on one class never disables a different class.
- **Replay cleanup is ordered.** A successful replay removes a signal's operational guard rows only after its append-only decision rows are durable. The audit record is written before the operational record is discarded, never the reverse.

3B's scheduled housekeeping is defence in depth behind these bounds, not the first bound.

### D.2 The parking transaction and the internal fault fact

Parking has **two transaction shapes (R3-04)**, distinguished by whether the class is already disabled when the parked signal arrives. Both commit atomically and both return the parked signal's own receipt; they differ only in whether they open a new fault generation.

**Shape 1 — the disabling parking transaction** runs for the fault that *first* disables a class, and is **parameterized by its disabling cause (R4-05)**, which is one of:

- `threshold` — the third identical deterministic failure (§D.1): parking decision `reason_code` = `parked_evaluation_faulted`, `disabled_reason` = `evaluation_fault`;
- `capacity` — a per-class retry-guard ceiling overflow (§D.1): parking decision `reason_code` = `retry_guard_capacity_exceeded`, `disabled_reason` = `retry_guard_capacity_exceeded`.

Both the decision's reason and the generation's `disabled_reason` are bound to the cause; neither is hardcoded. The transaction performs eight steps in order:

1. apply the triggering guard write (R4-01): the threshold cause's 2→3 upsert, or the capacity cause's ceiling-reaching insertion — this write commits only with the rest of the transaction;
2. insert the original event with disposition `stored_evaluation_faulted`;
3. insert its parking decision (`decision_mode` `live`, the cause's `reason_code` above, zero effects) and its `parked_evaluations` row in state `pending`, bound to the new generation from step 4;
4. disable the class in `disabled_condition_classes` by inserting the next-generation row (`fault_generation = max(existing generations) + 1`, per the §D.3 row lifecycle) recording the faulting pair and the cause's `disabled_reason`, with `cursor_event_id` null (R3-06: nothing replayed yet);
5. insert the deterministic internal evaluator-fault event;
6. run the sealed controller-diagnostic evaluator path;
7. append the fault decision, its effects, its transition, and any eligible intent;
8. commit, returning the original signal's receipt to the producer.

**Shape 2 — the reduced parking transaction** runs for a signal that arrives while its class is *already* ingestion-disabled (`state` `disabled` **or** `promoting` — R8-02). The class was disabled by an earlier shape-1 fault, so re-disabling it, opening a new generation, and emitting a second diagnostic fact would all be wrong — the fault episode is already open and one generation already owns the replay work. It performs only:

1. insert the original event with disposition `stored_evaluation_faulted`;
2. insert its parking decision (`decision_mode` `live`, reason `parked_evaluation_faulted`, zero effects) and its `parked_evaluations` row in state `pending`, **bound to the current active generation** — the single `state IN ('disabled', 'promoting')` row for the class (§D.3, R8-02); an arrival during `promoting` lands above the fence, outside the promotion cohort, and awaits the next drain — carrying that generation's `faulting_policy_digest` and `faulting_evaluator_version`;
3. commit, returning the original signal's receipt to the producer.

Shape 2 opens **no** new generation and inserts **no** new internal fault fact. It only enrolls the arriving signal into the existing generation's replay backlog, so the eventual re-enable (§D.3) will re-evaluate it alongside every other event parked under that generation. This is the transaction behind the §C.2 matrix row "Signal for a disabled condition class". Neither shape ever runs without the triggering request's bytes in hand: shape 1 embeds the threshold or capacity guard write (R4-01), and shape 2 runs on an arriving request — there is no deferred or reconstructed parking path.

**Reserved identity.** The internal fact is attributed to producer `controller:evaluator` in domain `controller`. No such producer exists in the producer registry and none can be created (§C.5); the identity is a constant of the controller, not a credential.

**Bounded identifiers.** `signalId` and `occurrenceId` are a fixed prefix plus the SHA-256 hex of a canonical tuple `(conditionClass, faultingPolicyDigest, faultingEvaluatorVersion, faultGeneration)`:

```text
signalId     = "evfault-sig-" + <64 lowercase hex>   → 12 + 64 = 76 characters
occurrenceId = "evfault-occ-" + <64 lowercase hex>   → 12 + 64 = 76 characters
```

Both are 76 characters for every possible input, comfortably under the existing 128-character bounded-ID limit, and the implementation asserts that bound. The length is constant because the class name is hashed rather than embedded — the rejected `fault:<class>:<digest>:<count>` shape grew with the class name and could overflow exactly on the poison path, when reporting the fault matters most. Including the fault generation in the tuple gives each successive fault on the same class a distinct occurrence, so a later fault opens a new episode instead of colliding with a resolved one.

The fact's subject is the faulted condition class. Its canonical payload is exactly the five typed attributes §A.4 declares — identifiers, digests, and counters only. It never carries exception text, stack traces, or any attribute from the signal that faulted; those are the untrusted, unbounded values that made the signal poisonous.

**Sealed dispatch.** The fact traverses the same fact → decision → transition → projection path as any other, but dispatches to a minimal `evaluateControllerPolicyFault` rule that is independent of the faulting class's policy code. That rule cannot enter the retry guard and cannot synthesize another fault. If the internal fact or the diagnostic rule fails, the entire parking transaction rolls back and the failure is classified as a core controller/storage failure on the existing 503/507 paths — it never recurses, never produces a nested fault event, and never leaves a half-parked class.

Because the internal entry point constructs typed values the controller already holds, it **bypasses** the producer-facing gates 8 through 12 entirely — it does not run them and does not need to satisfy them. Those gates exist to constrain untrusted producer input, and nothing on this path is producer-supplied: the condition class, digests, versions, counters, and identifiers are all controller-held values. What stands in for the gates here is the canonical construction itself, plus the test obligation that the constructed payload matches §A.4's declared allowlist exactly.

**Intent purposes on the sealed path are derived by the path, not by the policy.** The sealed rule emits `controller_diagnostic` when a fault opens and `recovery` when a fault resolves (§D.3). It never consults `notifyOnTransitions`, which is why `evaluator_policy_fault` declares that field empty (§A.4).

**While a class is disabled**, its signals are accepted and parked as `stored_evaluation_faulted` without evaluation, through the shape-2 reduced parking transaction above — enrolled into the active generation's backlog, opening no new generation and emitting no new diagnostic fact. Receipts are still issued and replay/conflict semantics are unchanged. Other classes are entirely unaffected; only storage, database-integrity, or core-controller failures degrade global ingestion, on the unchanged 503/507 paths.

**Row lifecycle (F-01, extended by R8-02).** A class is **ingestion-disabled** exactly when a row with `state IN ('disabled', 'promoting')` exists for it; at most one such row may exist per class (a partial unique index over `condition_class WHERE state IN ('disabled', 'promoting')`). Everything this spec predicates on a class "being disabled" — shape-2 parking, frozen projections, the drain's scope — applies equally in both states: `promoting` never re-opens ingestion. The §D.3 re-enable transaction does not delete the row — it updates it to `state = 're_enabled'` and stamps `re_enabled_at`. A later fault for the same class inserts a **new** row with `fault_generation = max(existing generations for the class) + 1`, computed over all rows including re-enabled ones. Generations are therefore monotonic across the class's whole history: a policy reverted to a previously faulting digest still produces a fresh generation, so the §D.2 internal fault identity (which hashes the generation) never collides with an earlier occurrence, and the distinct-occurrence guarantee survives policy reverts.

**Replay eligibility is per class, and a failed target is the new baseline (R4-02).** Eligibility is evaluated against the generation's replay history, not only its immutable parking state — comparing forever against the original faulting pair would leave a target that already *failed* immediately eligible for indefinite retry. The rule has three cases, keyed on `active_replay_target_state`:

- **No active target (null):** the class is eligible when its current class digest differs from `faulting_policy_digest`, **or** its current `EVALUATOR_VERSION` differs from `faulting_evaluator_version`. Both halves matter: a policy fix and an evaluator-code fix are independently sufficient, and neither implies the other.
- **`draining`:** the target is unfinished, not failed — a budget yield, a shutdown, or an in-progress drain. The drain resumes under the *same* pair; no policy or evaluator change is required to continue.
- **`failed`:** a class-local replay failure occurred under the recorded target pair. That pair is **not eligible again**: the class becomes eligible only when the current pair differs from the *recorded active target pair* — the failed target, not the original faulting pair, is the baseline. A genuinely different pair opens a new active target with the full R3-05 backlog reset (stale-target `resolved` rows revert to `pending`, cursor to null).

In every case the registry snapshot digest is **audit context only** and never triggers replay — a change to some unrelated class is not evidence that this class was corrected.

**Replay targets are recorded and coherent (R3-05), and a target's canonical identity is the full tuple (R10-01), scoped to its class and generation (R11-01):** the operational target key is `(condition_class, fault_generation, policy_digest, evaluator_version, replay_target_epoch)` — never the bare pair, and never the bare digest/version/epoch triple across generations: the epoch is monotonic only *within* a fault generation, so a later generation of this class — or another class entirely — can legitimately reuse the same digest, version, and epoch numbers, and only the class + generation prefix makes the key globally unique (R11-01). Every operational clause below reads and writes that key; within one generation the `(policy_digest, evaluator_version, replay_target_epoch)` suffix is the discriminator between incarnations, and every consumer that can ever see more than one generation's rows — overlay construction, provisional-reference validation, the store-open probes — scopes by class and generation first. The first time eligibility is detected for a generation, the drain records the *current* class digest and evaluator version into that generation's `active_replay_target_policy_digest` and `active_replay_target_evaluator_version`, with `active_replay_target_state = 'draining'` and the next `active_replay_target_epoch` (R9-01 — incremented on every target opening, pair-repeat or not). A class-local failure during the drain sets the state to `failed` in the same chunk transaction that records the failed replay decision; a budget yield or shutdown leaves it `draining`. Every subsequent replay decision for a `parked_evaluations` row under this generation stamps that row's `latest_replay_target_policy_digest` and `latest_replay_target_evaluator_version` with the target pair the decision was produced under. The re-enable predicate below requires that every outstanding parked event's latest replay decision was produced under the *current* active target **tuple** (R10-01); a mid-drain policy or evaluator change is therefore not a race but a bookkeeping event with a defined semantics:

- When the *current* class digest or evaluator version changes while a generation still has parked work, the drain observes the change on its next chunk boundary, opens a new active target pair on that generation, and — atomically in the same transaction — resets every non-`promoted` `parked_evaluations` row for the generation whose `state = 'resolved'` and whose **`latest_replay_target_epoch` differs from the newly opened epoch** — the epoch is the reset criterion, so rows resolved under an abandoned earlier incarnation of a **byte-identical pair** are reset too (R10-01) — back to `state = 'pending'`, and resets the generation's `cursor_event_id` to null; `promoted` rows are terminal realized history and are never reset (R7-02).
- **Immutable decisions are retained across the reset.** The append-only `evaluation_decisions` (plus effects, intents) already appended for the pre-change target pair are never deleted or altered — resetting a row is an operational-projection change only, and the audit trail contains every replay decision that was ever produced, tagged with the target pair it ran under.
- A failed replay for a row records the attempted target's **full tuple** — pair and epoch (R10-01) — on that row's `latest_replay_target_*` columns even though `state` remains `pending`, so a later target change likewise resets the failure attribution.

This makes the target coherent by construction: no re-enable can ever be predicated on decisions produced under a target the class no longer has.

**The drain is a controller-owned, lifecycle-managed background loop**, triggered after startup, after policy activation, and after newly parked work appears. It is not part of any request path.

- Each transaction handles at most **100 events**, in ascending `event_id`.
- Each event-loop turn handles at most **1,000 events**; the loop then yields and reschedules itself.
- It stops on shutdown (target stays `draining`, resumable under the same pair) or on a class-local failure (target set to `failed` — that pair is not retried; R4-02).
- These are **scheduling limits, never semantic drop limits**. Hitting a budget ends a turn; it never abandons an event, never advances past one, and never re-enables a class.

**Replay is staged; only promotion touches authority (R6-01).** A drain writes **no live authority**: no `incidents` row is updated, no `transitions` row is inserted, and no `notification_intents` row is created while a target is being replayed. What each chunk commits is staged audit — replay decisions and their effect rows — plus operational bookkeeping (`parked_evaluations`, cursor, high water). Three rules make this coherent:

- **The overlay snapshot.** The evaluator input for each replayed event is the live projection state overlaid with the current target's already-staged effects, applied in event order. **Overlay membership is exact and cohort-scoped (R11-01):** an effect enters the overlay only when it is reached *through* a `parked_evaluations` row that (1) belongs to the **active condition class and fault generation**, (2) has `state = 'resolved'` — never `promoted`: a `promoted` row's effects are realized history whose episodes already exist in live authority and enter the evaluator input through the live projections, so re-admitting their staged form would apply the same history twice — and never `pending`, (3) names the effect's decision as its `latest_replay_decision_id` — an effect of a superseded earlier staged decision for the same event never contributes — and (4) carries the complete active target tuple: `latest_replay_target_policy_digest`, `latest_replay_target_evaluator_version`, and `latest_replay_target_epoch` all equal to the active target's (R10-01). Membership passes through the active generation's parked rows — never by quantifying over staged decisions or effects directly — so append-only effects from an earlier fault generation, or from a later one that reuses the same digest, version, and epoch numbers, are structurally excluded (R11-01), and an abandoned incarnation's effects never enter the overlay. The pure evaluator is unchanged; the store computes the overlay. The overlay is sound because **a disabled class's live projections are frozen**: every arrival parks through shape 2 without evaluation, and no other path mutates that class's episodes, so nothing can invalidate the overlay's version arithmetic between staging and promotion (H-06 predicate 3 additionally guards the boundary). **Forward obligation for Plan 4 (R7):** locked §5's audited manual closure will break this premise; the operator spec must either forbid condition-projection mutations for classes holding staged replay work, or fingerprint the staging base and abort/rebase promotion when an operator mutation lands.
- **Staged effect rows carry `transition_id` NULL, permanently.** The transitions they imply do not exist until promotion; each staged effect's realization — its incident and its transition, if any — is recorded in `replay_promotions` keyed by `(decision_id, effect_ordinal)` (R7-01), the authoritative per-effect join; `transitions.decision_id` (§B.4) is denormalized convenience.
- **Failed and superseded targets remain audit-only.** Their staged decisions and effects are never promoted and never acquire transitions or intents. Because intents are created **only at promotion**, an unverified target's intents are structurally non-dispatchable — they never exist as rows. This is what makes the R3-05 reset (resolved→pending, cursor→null) genuinely complete: live authority was never touched, so there is nothing to roll back or compensate, and the next target evaluates against exactly the pre-fault authoritative state plus its own fresh overlay.
- **An episode realized by an earlier cohort is live authority (R11-01).** When a drain — the same target resumed after activation returned the generation to `disabled`, or any later target — evaluates an event whose verdict touches an episode whose staged opening has been promoted, the staged effect targets that episode as `target_kind = 'live'` with the realized `incident_id` (resolved through `replay_promotions`), exactly as it would any episode that existed before the fault; a `provisional_ref` to a realized opening is invalid at staging, enforced transactionally and at store open by §B.2's referential-validity rule.

**The cursor advances only through the contiguous successful prefix, starting at the beginning when null (R3-06).** `cursor_event_id` is nullable and its null value has a precise meaning: *nothing has been replayed yet under this generation's current active target pair*. The contiguous prefix therefore starts at the lowest **outstanding** (non-`promoted`; R8-01) `parked_evaluations.event_id` for the generation — completed cohorts are not part of any later drain's domain. This is the state a generation holds when it was just disabled (§D.2 shape 1 inserts the row with a null cursor), when the target pair has just changed (R3-05 resets the cursor to null), or when the drain has never had a chunk-boundary opportunity to run. When an event replays successfully, its chunk transaction — the same one that appends the **staged** replay decision (R6-01) carrying its immutable `replay_attempt_ordinal` (R6-02) — sets its `parked_evaluations` row to `state = 'resolved'`, records `latest_replay_decision_id` and the **full target tuple** — `latest_replay_target_policy_digest`, `latest_replay_target_evaluator_version`, **and `latest_replay_target_epoch`** (R10-01) — increments `replay_attempt_count`, and moves the cursor to the event (F-03: this is the one and only writer of `resolved`). When an event fails, the drain for that class stops there: the event keeps `state = 'pending'`, receives an appended replay decision recording the failure with an incremented `replay_attempt_count` and the attempted target pair, and **remains at the cursor boundary**. **The failure decision's durable shape is exact (R5-03):** `decision_mode` `replay`, reason `replay_attempt_failed`, disposition `stored_evaluation_faulted` (the event's committed disposition — a failed replay changes nothing about the fact), zero effects, zero intents, and `supersedes_decision_id` pointing at the event's latest prior decision. The evaluator's exception is not an `EvaluationDecision`; the store synthesizes this record from controller-held values only — class, digests, versions, and the attempt ordinal, recorded immutably on the decision's own `replay_attempt_ordinal` column (R6-02) so historical failures are reconstructible from append-only facts without consulting the mutable `parked_evaluations` aggregate — never exception text. **The chunk transaction commits the failure atomically with the chunk's progress:** one transaction persists the chunk's contiguous successful prefix (their decisions, effects, resolved rows, and cursor advance), the failure decision, the incremented attempt count, the `latest_replay_target_*` stamp, and `active_replay_target_state = 'failed'` (R4-02); the cursor ends at the last successful event. A crash before that commit rolls back the entire chunk — no partial failure record and no lost prefix, because the drain rediscovers both from durable state. The cursor never moves past a failed event, so a failure can never end up behind the cursor where it would be invisible to the zero-pending check.

**Mid-drain arrivals are not lost.** At the start of a drain the worker records `replay_high_water_event_id`. Events parked while that drain runs fall above the high water and are simply out of the current range. On finishing the range the worker captures the next high water and continues within its remaining budget. Nothing is skipped and no arrival can slip between the last processed event and the re-enable check.

**Re-enabling is one atomic transaction with a three-part predicate.** The class is re-enabled, and its fault resolved, only when all three hold, evaluated together in the same transaction that performs the re-enable:

1. no `pending` row remains in `parked_evaluations` for the class's active generation (R8-01: `promoted` rows never count as outstanding);
2. the class's *current* policy digest and evaluator version still equal the active generation's `active_replay_target_*` pair, **and** every **non-`promoted`** `parked_evaluations` row for this generation carries a `latest_replay_target_*` pair **and epoch** equal to the active target's (R9-01: epoch equality is what excludes an abandoned earlier incarnation of the same pair; R3-05 coherence over the outstanding backlog; R8-01: terminal `promoted` rows are a completed earlier cohort — realized history under their own fenced target — and are excluded from every later target-coherence, cursor, high-water, reset, and zero-pending calculation, so a mid-promotion target change can never strand the class behind rows that cannot be reset);
3. `cursor_event_id` and `replay_high_water_event_id` are unchanged from the values the drain finished with, compared **null-safely** (R9-02). For a non-empty outstanding domain a null cursor at this point remains impossible — resolving the domain necessarily advanced it — but for the **empty outstanding cohort** (below) null cursor, null high-water, and a null fence boundary are the valid, expected values.

Predicate 2 catches every category of mid-verification change: a policy or evaluator change that lands after the drain completed but before the re-enable transaction, **and** any decisions in the backlog produced under an earlier target pair the class has since moved off. Predicate 3 catches a concurrent drain or new arrival moving the boundary underneath the verifier. When all three hold, the class enters the **bounded promotion pipeline (R6-01, bounded by R7-02)** — three phases, only the first and last of which are single transactions:

1. **Fence** — one constant-size transaction re-verifies the three predicates and sets the generation's `state = 'promoting'` with `promotion_cursor_event_id` null, incrementing `promotion_cohort_ordinal` (from null to 1 on the generation's first fence; R15-01) — the durable identity every mapping row this cohort's promotion writes will carry. The fenced target pair and the verified cursor/high-water define the **promotion cohort (R8-01)**: exactly the `resolved` rows the predicates verified. From this commit on, the cohort and its verdicts are fixed durable facts; rows parked after the fence are outside the cohort and stay `pending` for a later drain.
2. **Promotion chunks** — bounded exactly like the drain (at most 100 events per transaction, ascending event order), resumable from `promotion_cursor_event_id`. Each chunk mechanically realizes its events' staged verdicts: episodes are inserted (provisional handles acquire real `incident_id`s) or updated per the staged effects, `replay_promotions` rows record each `(decision_id, effect_ordinal)` → realized incident/transition, `transitions` rows are created with `decision_id`, intents are created from the persisted `evaluation_decision_intent_specs` (R7-01) with `evaluation_decision_intents` rows, parked rows move to terminal `state = 'promoted'`, and the promotion cursor advances. No evaluator and no policy is consulted — this is realization of already-verified verdicts, so **a registry change during `promoting` does not abort promotion**: the verdicts were verified under the fenced pair, and their realization is committed history exactly as live decisions survive later policy changes. A crash resumes from the promotion cursor; the `replay_promotions` primary key makes re-realization impossible. **Promotion preconditions are defined per `target_kind` (R14-01), and every comparison reads the transaction-current authoritative row (R12-01/R13-02, corrected by R14-02):** for **`provisional_open`**, no incident row exists yet and none is read — the precondition is that the effect's prior fields are null (the R9-03 opening shape) and that no `replay_promotions` row exists for its `(decision_id, effect_ordinal)`; the chunk then inserts the incident from the effect's result fields and records the `replay_promotions` mapping in the same transaction. For **`provisional_ref`**, the referenced opening is resolved to its realized `incident_id` through the `replay_promotions` mapping written earlier in the same transaction or by a committed earlier chunk **of the same active cohort** — the mapping must carry the current `promotion_cohort_ordinal` (R15-01); a mapping from a completed earlier cohort fails the chunk closed, because that episode was live authority at staging time and the effect must have been staged `live` (R13-01) — and the effect's `prior_state` and `prior_projection_version` are compared against that incident's transaction-current projection. For **`live`**, the effect's own `incident_id` resolves the row directly; its priors are compared against the transaction-current projection. **Transaction-current means read-after-write (R14-02):** each precondition read occurs on the same transaction and connection, after every preceding effect's writes in that chunk, and therefore observes them even though they are not yet committed externally; a cached transaction-entry projection is forbidden. Promotion runs on exactly **one** SQLite connection (R15-03): a mapping or projection lookup through any second connection — one that could not observe the chunk's uncommitted writes — is forbidden. The first effect processed after a restart reads the durable committed prefix — the same rule, with no preceding in-transaction writes to observe. Predecessor continuity is explanatory, not operational: after one effect is applied, the transaction-current row necessarily equals that predecessor's result, so the single read-after-write comparison subsumes the chain link; the predecessor's identity is never derived from process memory, and no in-memory value may substitute for the row read. Every branch retains per-effect idempotence (`replay_promotions` PK), ordered application, and full-chunk rollback. A mismatch — or any per-kind precondition violation — fails the chunk closed: the transaction rolls back in full — no transitions, no intents, no parked-row state changes, and no promotion-cursor advancement — and the condition is classified as a core storage integrity failure (impossible while projections stay frozen; observing it means corrupted staged state), fail-closing incident ingestion per the R4-07 degradation contract rather than committing partial authority.
3. **Activation** — one constant-size transaction requires `promotion_cursor_event_id` to equal the fence boundary; then, if the current pair still equals the fenced target AND zero `pending` rows exist, it emits the recovery fact below and sets the generation to `state = 're_enabled'` with `re_enabled_at` (per the row lifecycle — never a delete). Otherwise it returns the generation to `state = 'disabled'`: the promoted work stands (it is verified, realized history), and the pending arrivals await the next eligible drain.

Every phase's write cost is bounded independently of backlog size — the fence and activation are constant, and each promotion chunk is capped — satisfying the locked bounded/resumable replay contract for the authority switch as well as the drain.

**The empty outstanding cohort (R9-02).** A generation whose outstanding (non-`promoted`) domain is empty — the state left behind when an earlier cohort promoted fully but activation returned the generation to `disabled` (pair changed mid-promotion) and no arrivals followed — is a first-class case, not an impossibility. For it, `cursor_event_id`, `replay_high_water_event_id`, the fence boundary, and `promotion_cursor_event_id` are all validly NULL and every comparison over them is null-safe. An eligible drain over an empty outstanding domain performs a **zero-row fence and activation under the current pair, in a new target epoch (R9-01)**: the fence predicates hold trivially over zero rows, promotion realizes nothing, and activation emits the recovery fact and re-enables — the backlog is fully realized, so there is nothing left to verify. **Activation always reschedules the drain (R9-02):** when activation returns a generation to `disabled` instead of re-enabling, the same transaction's commit triggers a fresh drain-eligibility evaluation, so a policy-change trigger that fired (and was consumed) during `promoting` can never be lost — the empty-cohort zero-row pass above is exactly how that rescheduled drain completes. **Intent dispatchability, refined (R7-02):** intents exist only for a fenced (verified) target — an unverified or failed target never produces an intent row — and they materialize incrementally during that target's promotion chunks rather than at activation; verification always precedes the first intent's existence. If any fence predicate fails, the fence transaction makes no change: the class stays disabled, the fault episode stays open, and the next drain re-evaluates from the current state — including, if predicate 2 failed on the coherence half, resetting stale-target `resolved` rows back to `pending` (R3-05; `promoted` rows are terminal and never reset).

**The activation transaction is the only writer of `policy_replay_verified` (H-05).** It emits the controller recovery fact — a `condition_recovered` fact on `evaluator_policy_fault`, through the same reserved identity (`controller:evaluator` in domain `controller`) and sealed path as §D.2 — which resolves the fault episode. No other path can resolve that episode: not a manual signal, not a partial drain, not a registry change. A partial or failed replay leaves the class disabled and the fault open.

**The recovery envelope is completely bound (R3-07).** Every field is derived from committed state, none from the wall clock or from producer input:

| Field | Value |
|---|---|
| `producerDomainId` | `controller` — the reserved identity, same as the fault fact |
| `producerId` | `controller:evaluator` |
| `kind` | `condition_recovered` |
| `subject` | the faulted `conditionClass` — same as the fault fact |
| `conditionClass` | `evaluator_policy_fault` |
| `signalId` | `"evfault-rec-" + <64 lowercase hex of SHA-256(conditionClass, faultingPolicyDigest, faultingEvaluatorVersion, faultGeneration)>` — 76 characters, distinct from the fault fact's `evfault-sig-` prefix so replay/conflict on the two facts never collide |
| `occurrenceId` | the **same** `evfault-occ-…` occurrence id as the generation's opening observation, so the recovery closes the exact episode the fault opened |
| `occurrenceSeq` | **strictly greater** than the observation's: the fault-opening observation is `occurrenceSeq = 1`, the recovery is `occurrenceSeq = 2`. Any future controller-emitted correction on the same occurrence would continue the monotonic sequence — 3A emits only 1 and 2 |
| `observedAt` | the re-enable transaction's own `evaluationTime` — i.e., the exact evaluation time this transaction records on its decision row — not the wall clock and not any parked event's timestamp |
| `recoveryProofClass` | `policy_replay_verified` |
| `attributes` | the same five typed attributes §A.4 declares, mirroring the opening fault fact so audit tooling can join them on `(faultingConditionClass, faultingPolicyDigest, faultingEvaluatorVersion, faultGeneration)` |

The **identity fields** — `signalId`, `occurrenceId`, `occurrenceSeq` — are generation constants, deterministic for every possible execution. `observedAt` is deliberately **not** a generation constant (R4-06): it is the committing transaction's evaluation time, so a re-enable that crashes before commit and is later retried constructs an envelope with a later `observedAt`. No byte-identical-retry property is claimed, and none is needed — the idempotency boundary is structural, not byte-level: H-05's single atomic transaction either commits the recovery fact once or leaves no trace, and any duplicate emission attempt collides on the events table's `UNIQUE (producer_id, signal_id)` through the deterministic `evfault-rec-` signal id, surfacing as a conflict rather than a second fact. At most one recovery fact per generation can ever exist, whatever its timestamp.

**Originals are never mutated.** A drain appends staged decisions and effect rows and updates only the operational projections (`parked_evaluations.state`, the cursor, the high water); transitions and intents come into existence exclusively at promotion (R6-01). Every parked event keeps its original row, disposition, `initial_decision_id`, and the receipt its producer already holds.

## E. Testing and guard obligations

**Migration v3.** Fresh-create at v3; v2 upgrade preserves all rows, including `events` byte-for-byte across the rebuild (digest the table contents before and after); the `sqlite_sequence` AUTOINCREMENT identity survives the rebuild; ahead-version still fails closed; crash-resume (v2 applied, v3 missing). Plus the H-04 fault-injection suite: an exception after **each** destructive phase, injected inside the production `BEGIN IMMEDIATE` transaction, each run asserting exact rollback to v2 — schema, rows, checks, indexes, next identity — then a clean unmodified run to v3. Testing a statement prefix outside the transaction is forbidden and its absence is itself asserted. **The injection seam is named (F-08):** `openIncidentDb` accepts a test-only `migrationFaultInjection?: (statementIndex: number, statement: string) => void` option threaded to `applyMigrations`, invoked between statements inside the transaction; production callers never pass it, and the option's absence changes no behavior — tests get a real in-transaction seam without a bespoke branch hacked into `db.ts`.

**Policy registry.** Per-class digest determinism and order-insensitivity; a registry-only change leaving every sibling class digest byte-identical while the snapshot digest changes; duplicate `conditionClass` throws; a duplicate element in every set-like field throws; the closed `severity`, `retentionClass`, `permittedKinds`, and `notifyOnTransitions` sets; a safe-identifier grammar violation in each registry-side field §A.2 rule 3 enumerates, and an `attributeAllowlist` key that is a valid safe identifier but exceeds the envelope's 64-character key bound; every `AttributeSpec` rejection in §A.2 rule 5; the H-02 cadence group matrix; §A.2 rule 7, that a controller-owned class declaring a non-empty `permittedKinds` or `permittedSubjects` throws; §A.2 rule 8, that a `conditionClassRef` `allowed` member naming an absent class throws, and that an `evaluator_policy_fault` allowlist whose `allowed` set omits any registered class throws. **Digest-identity falsifier (R5-01):** registries R1 and R2 built from byte-identical `source` policy declarations but a changed sibling-class set must leave the `source` per-class digest byte-identical AND its accepted attribute-value set identical (adding, removing, and remove-then-re-adding the sibling), across ingestion acceptance, retry-guard keys, historical audit reads, and parked replay — proving acceptance is a pure function of digest-covered bytes.

**Attribute semantics.** One accept and one reject per `AttributeSpec` kind, including a non-integer number for `int`, an out-of-range integer, an uppercase or malformed `sha256:` digest, an unknown enum member, and — for `conditionClassRef` — a grammatically valid name outside the spec's `allowed` set, including a class that IS registered but not listed (R5-01: gate 11 consults only the digest-covered set). Plus the **realistic-corpus falsifier (R4-03)**: the command token `whoami`, the cache-key shape `msg-cached`, and the WhatsApp-style message id `wamid.HBgM123` must each be rejected by *every* producer-controlled attribute kind — as non-members for `enum`, as non-members of the digest-covered `allowed` set for `conditionClassRef`, as malformed for `digest`, and as non-numeric/non-boolean for `int`/`boolean` — unless a policy has explicitly enumerated that exact value in an `enum`. A signal whose *identity* fields carry identifier-shaped or non-ASCII values (such as `€`) is still accepted, proving no attribute tightening leaked onto the wire contract. No value is ever coerced or stripped.

**Dispatch equivalence.** The full existing incident suites pass under fixture registries with byte-identical receipts.

**Enforcement and decisions.** The §C.1 gate order end to end, asserting for each rejecting gate that zero event, decision, effect, transition, intent, and guard rows exist afterwards; the §C.2 matrix row by row, asserting exactly one decision per accepted condition evaluation and the correct disposition and reason; an exact-byte replay returning the original receipt while creating no decision; heartbeat and notice acceptance creating no decision. **Failure matrix rows (R3-09):** deterministic failures 1 and 2 must return 503 `internal_error` (retryable) with zero event/decision/effect/transition/intent rows and exactly one `evaluation_retry_guard` upsert (the guard row is not a gate rejection and matrix rule 3 covers it); failure 3 must return 201 with the parked signal's receipt and one event + one decision row from the §D.2 shape-1 transaction; the sequence 503 → 503 → 201 on three identical failures is one atomic assertion pair.

**Identity answering survives tightening (§C.1).** A signal accepted under one schema, scope grant, and registry is resent byte-for-byte after each of three independent tightenings — the envelope schema rejects its shape, its producer's scope no longer admits it, and its condition class is removed from the registry — and each resend must return 200 with the original receipt byte-for-byte and create no new event, decision, effect, transition, intent, or guard row. The same three tightenings with *different* bytes on the stored identity must each return 409 `signal_identity_conflict`, never 422 or 403. A route that validates schema or scope ahead of the store's identity short-circuit fails these tests, which is what makes the §C.1 ordering falsifiable rather than merely asserted.

**Decision cardinality.** A state-inert decision with zero effect rows; a supersession decision whose effect count is N + 1 for N superseded open episodes, with dense ordinals and correct prior/result state and projection versions; a decision creating several ordered intents; and a check that no JSON array anywhere carries authoritative foreign keys. **Intent-to-effect binding (R3-08):** a supersession-plus-onset decision produces exactly one `onset` intent whose `effectOrdinal` selects the opening effect (not any superseded effect), and the persisted `notification_intents.transition_id` and `causing_projection_version` equal the values the store wrote on that selected effect's row; an `IntentSpec` with an out-of-range `effectOrdinal`, a projection-only target effect, or a purpose disagreeing with the decision reason must roll the accept transaction back and store zero rows.

**Recovery envelope binding (R3-07/R4-06).** The re-enable transaction is asserted to emit a `condition_recovered` envelope with: `signalId` beginning `evfault-rec-` and 76 characters long; `occurrenceId` byte-equal to the generation's opening `evfault-occ-…` value; `occurrenceSeq` = 2 while the opening observation held `occurrenceSeq` = 1; `observedAt` equal to the transaction's own recorded evaluation time; `recoveryProofClass` = `policy_replay_verified`; and the same five typed attributes §A.4 declares. The identity fields must be byte-identical across a crash-and-retry with an advanced fake clock, while `observedAt` differs — and the retried emission must be the generation's only committed recovery fact, with a forced duplicate insertion colliding on `UNIQUE (producer_id, signal_id)` instead of creating a second fact.

**Parking and the fault fact.** Three identical failures park the event and disable the class through the §D.2 shape-1 (disabling) parking transaction, which opens a new `disabled_condition_classes` generation and emits the internal fault fact exactly once; a different payload, policy digest, or evaluator version is a different key and restarts the count; an unrelated class's policy change does not reset the guard key; class isolation, so other classes stay ingestible; the internal fault identity is deterministic and both identifiers are exactly 76 characters for a maximum-length class name; the canonical payload carries only the five declared attributes; and injected failure of the sealed diagnostic rule rolls the whole shape-1 transaction back as a core failure with no nested fault event. **Reduced parking (R3-04):** a second, third, and fourth signal for the already-disabled class each run the §D.2 shape-2 reduced parking transaction — each stores its event and `parked_evaluations` row bound to the *same* active `fault_generation`, and none of them inserts a new generation row or a new internal fault event; the fault episode remains exactly one, and the replay-work backlog for that generation grows by one row per arrival.

**Retry-guard capacity.** Unique failing signals below the three-failure threshold stop at the ceilings rather than growing without bound; age pruning never removes a row whose parked work still exists; overflow parks and disables with `retry_guard_capacity_exceeded` instead of dropping the signal; guard rows are removed only after the replay decisions are durable. The guard row records the envelope's `condition_class` at failure time and the ceiling counts rows per that stored class, so failures 1 and 2 — which store no event row — are still attributable to a class. **Atomic threshold parking (R4-01):** a crash injected inside the combined third-failure transaction — after the guard write, before commit — must roll the guard back to `failure_count = 2` with zero event, decision, parking, generation, and fault-fact rows; reopening the store must find no integrity violation; the producer's byte-identical resend must then re-run evaluation, fail, and complete the combined transaction normally, with the guard reaching 3 exactly once and the parked receipt returned; the same injection into the capacity-cause combined transaction must leave the guard-row count unchanged. The store-open integrity probe must fail closed on a forcibly persisted guard row with `failure_count >= 3` and no `parked_evaluations` row. **Cause binding (R4-05):** threshold parking must produce decision reason `parked_evaluation_faulted` with `disabled_reason` `evaluation_fault`, and capacity parking decision reason `retry_guard_capacity_exceeded` with `disabled_reason` `retry_guard_capacity_exceeded` — one exact-row assertion per cause. **Ceiling pre/postconditions (R4-04):** the insertion that would reach 256 rows for a class runs capacity parking rather than growing the guard; a forcibly persisted 257-row state for a registered class fails the store-open integrity probe as a core storage failure without disabling any unrelated class. **Derived-bound scoping (R3-10):** removing a class from the registry preserves its historical `evaluation_retry_guard`, `parked_evaluations`, and `disabled_condition_classes` rows; the derived bound counts rows for currently registered classes only, so a contraction that leaves preserved rows above the new derived total must pass the probe cleanly. **Active-pair scoping and continuation (R5-02/R6-03):** populate 255 distinct sub-threshold rows under pair D1, activate pair D2, and prove the first distinct D2 failure records `failure_count = 1` with no capacity parking while every D1 row is still present in the table (retained, not deleted); repeat with a D1 capacity generation whose parked event replays successfully under D2 (the class must remain enabled afterwards); with class removal and re-addition. **Pair-revert continuation (R6-03):** drive one identity to `failure_count = 2` under D1, activate D2, revert to byte-identical D1, and prove the identity's next failure parks at 3 through the shape-1 threshold transaction — the exact five-part-key history must survive the toggle; a `failure_count` outside 1–3 must be rejected by the SQLite CHECK itself.

## F. Hardening obligations

These six obligations are binding requirements of this design, not advisory notes. Each names where it is specified and what would falsify it.

**H-01 — Canonicalization rejects rather than normalizes.** Duplicate elements in any set-like policy field are rejected at registry construction (§A.2 rule 2); only already-validated sets are sorted, and only for hashing, without mutating the registered policy (§A.3). The per-class digest and the registry snapshot digest are separate definitions with separate consumers (§A.3). *Falsified by:* two materially different policy sources producing the same digest, or `get()` returning a reordered policy.

**H-02 — Cross-field policy validation is complete at construction.** `expectedCadenceMs`, `graceMs`, and `staleMs` are finite safe integers with `expectedCadenceMs > 0`, `graceMs >= 0`, `staleMs > graceMs`, supplied as a complete valid group or wholly absent (§A.2 rule 6). Invalid values still fail registry construction even though no 3A code path consumes them. *Falsified by:* a registry with a partial or inconsistent cadence group building successfully.

**H-03 — The retry guard is bounded within 3A.** Age pruning that never touches a row with parked work; a per-class enforcement ceiling of 256 **active-pair** rows evaluated against the triggering class only (R5-02/R6-03: stale-pair rows stop counting on pair change by pair scoping alone and are retained as durable audit until age pruning, so a repaired policy starts with a clean budget while a pair revert continues its exact-key history), whose reaching insertion runs capacity parking atomically (R4-01/R4-04); a derived global capacity of `256 × currently-registered class count` computed by the pure registry builder and verified by the store-open data-dependent probe (R4-07), scoped to currently-registered classes (R3-10: rows for a since-removed class stay preserved but are excluded from the bound, so a registry contraction never trips the alarm); and an overflow path that parks and disables the offending class rather than dropping evidence (§D.1). *Falsified by:* authenticated unique failing signals growing one class's active-pair guard rows past its ceiling, a healthy class disabled by another class's growth or by stale-pair rows surviving into a repaired pair's budget (R5-02), a pruned row whose parked work still exists, a stale-pair row deleted before its 30-day retention expires other than through the declared cardinality compaction (R6-03/R9-04), an overflow that discards a signal, a class removal that either deletes its historical guard/parked/disabled rows or trips the probe, or a registry builder that reads database state.

**H-04 — Migration tests exercise the real transaction.** Tests inject an exception after **each** destructive phase of the actual v3 migration — creating the replacement `events` table, copying its rows, dropping the original, renaming the replacement, and restoring the `sqlite_sequence` identity — while execution is inside the production `BEGIN IMMEDIATE` transaction that `src/fleet/incidents/db.ts` already wraps every numbered migration in.

Each injected run must roll back **exactly** to v2, preserving schema, rows, `CHECK` constraints, indexes, and the next AUTOINCREMENT identity. Reopening the database and running the unmodified migration must then reach v3 cleanly.

Executing a statement prefix outside the transaction is **forbidden** as a test technique. It exercises a state the production code cannot reach, and it would pass while transactional rollback is broken — which is the only property this test exists to prove. *Falsified by:* a rollback that leaves v2 altered in any respect, or a resumed migration that does not reach a clean v3.

**H-05 — Only the atomic zero-pending path resolves a fault.** The single re-enable transaction in §D.3 is the only writer of `policy_replay_verified` and the only path that can resolve an `evaluator_policy_fault` episode. *Falsified by:* any other path — manual signal, partial drain, registry change, operator action — resolving that episode.

**H-06 — Cursor and arrival safety are checked atomically.** The zero-pending predicate, the target policy/evaluator pair, and the cursor/high-water pair are compared together in one transaction (§D.3). Arrivals during a drain either extend the next bounded drain or leave the class disabled. *Falsified by:* a class re-enabled while a pending row exists, while the target pair has changed, or while the boundary moved underneath the verifier.
