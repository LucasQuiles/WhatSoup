## Finding Detail

### A1 — Idempotency ledger cross-operation collision (functionality, medium)

**Evidence:** `src/transport/testing/in-memory.ts:74,211-213,265-266`
- Line 74: `private readonly idempotencyLedger = new Map<string, MessageRef>();`
- Line 211–213: `if (opts?.idempotencyKey !== undefined) { const prior = this.idempotencyLedger.get(opts.idempotencyKey); if (prior !== undefined) return prior; }`
- Line 265–266: `if (opts?.idempotencyKey !== undefined) { this.idempotencyLedger.set(opts.idempotencyKey, ref); }`

The ledger key is the bare `idempotencyKey`. `sendCore` is shared by `sendText`, `sendMedia`, `sendVoiceNote`, and `sendWithButtons`. A caller that reuses the same `idempotencyKey` across two of these operations (legitimate at the application layer — they're different operations, different keys conceptually) gets the *first* operation's `MessageRef` returned for the *second* operation, and the second operation never executes.

**Why C19 didn't catch it:** `tests/transport/contract/conformance.test.ts` C19 ("idempotency declaration honored") probes within a single operation, not across operations.

**Suggested fix:** key the ledger by `${operation}:${idempotencyKey}` (or `[operation, key]` tuple), and add a C19b conformance test that re-uses the same key across `sendText` and `sendMedia` and asserts both execute independently.

**Distinction from existing task #51 (I3):** I3 is about `react`/`editText`/`deleteMessage` declaring `idempotency: 'simulated'` in capabilities while their implementations entirely bypass the ledger. A1 is a different bug — within the *send-family* (which DO use the ledger), keys collide across operations. Both should be fixed; A1 has higher correctness impact.

### A2 — `FanoutDispatcher.dispose()` missing (resilience, medium)

**Evidence:** `src/transport/contract/fanout.ts:31-150` — only `flush()` exists, no shutdown.

The dispatcher cannot be cleanly shut down. There is no method to:
- Stop accepting new `subscribe` calls.
- Cancel in-flight `drainLoop` Promises.
- Cancel pending `setTimeout` timers.
- Drain remaining queued events to a teardown handler.

For long-running instance processes (`primary-line`, `operator-agent`) this is acceptable while the process lives, but on hot-reload, test teardown, or graceful SIGTERM, it leaves orphaned Promises/timers. Tests today work around this with `flush()` followed by Vitest teardown — fine for `--pool=forks` isolation, but a real bug in a non-forked context.

**Suggested fix:** add `async dispose(): Promise<void>` that:
1. Sets a `disposed` flag, `enqueue` returns early when set.
2. Sets `suspended = true` on every sub (so `drainLoop` exits its `while` cleanly).
3. Awaits `flush()`.
4. Clears `subs` map and metrics.

### A3 — Post-dispose drainLoop continues for queued events (resilience, low-medium)

**Evidence:** `src/transport/contract/fanout.ts:60`
- `return makeSubscription(() => { this.subs.delete(id); });`

When a subscription is disposed:
1. `subs.delete(id)` runs synchronously — new events from `enqueue()` no longer reach this subscriber.
2. But the active `drainLoop(sub)` holds `sub` via closure (lines 95–103) and continues until `sub.queue.size === 0` or `sub.suspended === true`.
3. Events already in `sub.queue` continue to deliver to the (now-disposed) handler.

Most callers will assume "after `dispose()` returns, no more invocations of my handler." That assumption is silently wrong here for already-enqueued events.

**Suggested fix:** in the dispose callback, also set `sub.suspended = true`. The next iteration of `drainLoop`'s `while (sub.queue.size > 0 && !sub.suspended)` exits, queue contents are abandoned. Faster than draining; matches caller expectation.

**Relation to existing task #50 (I2):** I2 covers Set mutation during dispatch in `InMemoryAdapter.injectInbound`'s `for (const h of this.listeners.message) h(...)` loop. A3 covers a different surface (`FanoutDispatcher` post-dispose). Both involve "what happens to in-flight delivery on dispose" but the code paths are independent.

### A4 — `RateLimitedError.retryAfterMs` lost in hint string (usability, medium)

**Evidence:** `src/transport/contract/errors.ts:81-90`
```ts
export interface RateLimitedInput extends BaseInput {
  readonly retryAfterMs?: number;
}
export class RateLimitedError extends TransportError {
  readonly payload: TransportErrorPayload;
  constructor(input: RateLimitedInput) {
    super(input.message);
    this.payload = build(ErrorCode.RATE_LIMITED, true, input,
      { hint: input.retryAfterMs ? `retry-after-ms=${input.retryAfterMs}` : input.hint });
  }
}
```

The constructor accepts a typed `retryAfterMs: number` but does not preserve it on `payload`. The only place it surfaces is as a stringified `hint`. Any downstream caller wanting to programmatically wait the recommended interval before retry must regex-parse `hint`.

This defeats the purpose of the typed error envelope for the one error class where machine-readable retry timing has the highest value.

**Suggested fix:** extend `TransportErrorPayload` with optional `retryAfterMs?: number` (or add a `RateLimitedPayload` extension type) and preserve the value structurally. Keep the `hint` for human-readable output.

### A5 — `BoundedQueue.dropped` counter is dead instrumentation (observability, low)

**Evidence:**
- `src/transport/contract/queue.ts:7` declares `dropped: number`.
- `src/transport/contract/queue.ts:52-57` `dropOldest()` is the only writer.
- `src/transport/contract/fanout.ts:67-86` is the only consumer of the queue's enqueue path. On overflow it suspends the subscriber (line 79); it never calls `dropOldest()`.

`dropped` is wired in but no production code path triggers it. Operators reading `counters.dropped === 0` cannot tell whether (a) no drops have occurred, or (b) the policy is suspend-on-overflow and drops never happen by design.

**Suggested fix:** either (a) remove `dropped` and `dropOldest` until a transport actually uses drop policy, or (b) document explicitly in `queue.ts` that `dropOldest()` is unused by the current `FanoutDispatcher` policy and exists for future drop-policy adapters.

### A6 — `oldestAgeMs() === 0` is ambiguous (observability, very low)

**Evidence:** `src/transport/contract/queue.ts:59-62`
```ts
oldestAgeMs(): number {
  const head = this.buf[0];
  return head === undefined ? 0 : Date.now() - head.enqueuedAt;
}
```

Returns 0 in two semantically different cases: queue is empty, or queue's head was enqueued within the same millisecond. A monitoring consumer that pages on `oldestAgeMs > 60000` is fine; a consumer that reasons about queue health based on `oldestAgeMs` alone is mildly confused. Probably not worth touching, but flagged.
