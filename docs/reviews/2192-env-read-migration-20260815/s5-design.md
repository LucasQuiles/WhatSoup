Layer control functions (why four surfaces are not swiss cheese — each owns a distinct function/latency): **vitest counts** = reviewed-set constraint, unbypassable, CI latency; **markers** = site-level WHY at the place a reader looks (information, in-code); **eslint mirror** = fast feedback (editor/push minutes, not CI hours); **registry row** = machine-checked rule→backstop link. A `baseline.json` violationCount for this rule would duplicate the vitest counts at the same latency — rejected (also `meta.no-redundant-gates`, taxonomy `:183`).

## 3. Detail per question

### Q1 — Marker convention

- **Syntax:** `env-allowed: <reason>` — byte-shape of `console-allowed:` (`console-usage-budget.test.ts:45`). The string appears nowhere in src/ today (verified by `rg "env-allowed"` → zero hits), so no collision with prose.
- **Placement: same line OR the line above — both, exactly like console** (`console-usage-budget.test.ts:75-77`). Same-line trailing suits short reads (`const raw = process.env[key]; // env-allowed: bounded per-key resolver map`); line-above suits dense lines (e.g. `bot-errors-outbox.ts:283`, `runtime.ts:8024` which already wraps a conditional spread).
- **Multi-line reads:** the counting unit is ALREADY the line — "one site = one non-comment source line containing a process.env access" (`env-read-allowlist.test.ts:11-15`). Only lines bearing the literal `process.env` token count, so a read wrapped across lines has exactly one counted line and needs one marker on/above that line. A line with **two** tokens (7 exist today: config.ts, outbound-message-safety.ts, silence-registry-episode-store.ts:69, bot-errors-outbox.ts:283, claude-filestore-heal.ts:188, primary-model-usability-adapters.ts:286, runtime.ts:8024) is ONE vitest site → ONE marker. The eslint rule must dedupe to the same line grain (§Q3), or those 7 lines warn twice.
- **Interaction with per-file counts:** unchanged in the counting sense — marked lines still count (a marker is not a whole-line comment; `isCommentLine` only excludes lines that START as comments, `:141-144`). Markers add a second assertion in the same test file (console shape `:110-117`), and a new cross-assertion (§Q5).
- **Quality floor — adopt the catch rule's, not console's:** reason ≥16 chars and ≥3 words (`require-catch-justification.mjs:291-299`). Rationale: env sites route secrets/identity/toolchain; a bare `// env-allowed: tmp` is a magic word, exactly what the catch rule's `JUSTIFICATION_CLASS_RE` + floor was built to reject. Console could stay floor-less because its two survivors are one class in one file; env has 45 files of heterogeneous reasons.

### Q2 — SSOT: one shared source

**Studied precedents.**
1. *ring-boundaries:* the guard **runs the eslint rule itself** through `eslint.config.fitness.mjs` (`ring-boundary-guard.ts:52-76`) — detector SSOT is the rule; the shared data is just a count in `baseline.json` + doc twin. **Does not fit env:** the authoritative env ratchet is a *lexical* scanner whose comment-exclusion and line-counting conventions ARE its contract (`env-read-allowlist.test.ts:141-159`); re-basing it on the AST rule would change counting semantics mid-migration (the 7 two-token lines alone prove the grains differ), and the vitest test must stay suppression-immune (an eslint-disable must not be able to shrink it — the catch family needed a whole standalone `noInlineConfig` scanner for exactly that, `generate-catch-ratchet.mjs:76-91`; the lexical test is immune by construction).
2. *catch-ratchet:* rule + generator + tests share ONE data file, `eslint-rules/catch-ratchet-baseline.json`; the rule reads it via fs fail-closed (`readCatchBaseline`, `require-catch-justification.mjs:56-66`); the drift test pins rule scope to the file the baseline scans (`eslint-fitness-check.test.ts:61-67`). **This fits.**

**Design:** move the ALLOWLIST literal to `eslint-rules/env-read-allowlist.json` — an array of `{ "file": "src/...", "allowedUnmarkedSites": N, "reason": "..." }` rows (the reason field upgrades today's in-test comments to data, the `SsotAllowlistEntry {file, reason}` precedent at `ssot-pattern-guard.ts:78-97`; `allowedUnmarkedSites` semantics per §Q5 = the file's full pinned count at end-state). Consumers: the **vitest test imports it** (enforcement logic stays in the test — it remains the authority); the **eslint rule reads it via fs**, fail-closed on missing/corrupt JSON (`readCatchBaseline` shape). Drift between the two detectors is bounded by: (a) the pin tests (rule registered, scoped to exactly one `src/**/*.ts` block — new scope assertion cloned from `eslint-fitness-check.test.ts:61-67`); (b) the rule's line-grain dedup matching the lexical convention; (c) the rule's own unit test (`tests/eslint-rules/`, one per custom rule — 10 exist today). A future community `no-process-env` rule is NOT adopted: it has no marker/allowlist semantics; ours is the catch-rule pattern applied to env.

### Q3 — ESLint rule shape

- **File/name:** `eslint-rules/require-env-justification.mjs`, registered in `eslint-rules/index.mjs` as `fitness/require-env-justification` (mirrors `require-catch-justification` naming).
- **Registry row:** id **`arch.env-read-justification`** (architecture family — this is the config-SSOT discipline, sibling of `arch.ssot-*`), category `architecture`, detect `ast`, rings `['eslint','guard','ci']`, severity **`block`**, `ratchet: true`, `implementedBy: ['tests/scripts/env-read-allowlist.test.ts']`, params `{ baselinePath: 'eslint-rules/env-read-allowlist.json' }`. This is the `arch.ring-boundaries` dual-ring shape (registry `:448-458`): registry block severity enforced by the vitest test (curated at `push-gate.ts:75`, full CI suite), eslint ring stays a warn mirror. The `hygiene.catch-justification` warn-only shape (`:384-395`) is viable with less ceremony, but under-describes a rule that blocks today. **Cost of block shape:** one conscious line added to `TAG_PATH_UNCOVERED_BLOCK_RULES` (`fitness-registry-backing.test.ts:92-109`) — the backing test fails until it's added, by design; also satisfies non-vacuity (`:111-116`) and implementedBy checks (`:118-167`) with no further edits.
- **Detection:** flag any expression rooted at `process.env` — `MemberExpression` whose object chain reaches `process.env`: dot access, computed access `process.env['X']` (the DOMINANT form in src/), assignments (`process.env.X = v`), `delete`, deeper chains `process.env.X?.Y` (report the outermost node once), and bare whole-object value refs (`= process.env` param defaults at arc-binding-health.ts:35 / health-bind-guard.ts:24 / fleet/bind-guard.ts:23 / claude-filestore-heal.ts:253, `Object.entries(process.env)` at ops-auth.ts:64, `resolveReleaseIdentity(process.cwd(), process.env)` at capability-obligation-runtime.ts:693). **Dedupe to one finding per line** so the rule's grain equals the vitest line grain (7 two-token lines otherwise double-warn).
- **Exemptions, in order:** (a) site marker on the same line or line above, passing the quality floor (§Q1); (b) else count the file's unmarked lines and stay silent while `unmarked ≤ allowedUnmarkedSites` from the JSON (the allowlist-count mirror — this is what keeps the 5a transition window warn-free: with zero markers committed, unmarked == pinned == allowed → zero warnings, exactly like catch's baseline absorbing its 127 identities). Findings name the remediation ("route through src/config.ts or add an `env-allowed:` justification") and, catch-style, may embed a stable identity for debuggability.
- **Severity: warn in eslint.config.fitness.mjs** — every eslint-ring rule is warn (`eslint.config.fitness.mjs:30-31`; taxonomy `:313-329` "Advisory mirror; the blocking ratchet lives beside it"). Wiring: new dedicated block `files: ['src/**/*.ts']` (matching the vitest scanner's srcRoot — the catch scope-test pattern), a `ruleEntriesFor` case, index.mjs registration. Do NOT add a `violationCount` row to `.claude/fitness/baseline.json`: it would re-encode the per-file counts as a single total at the same latency as the vitest test — same control function, second barrier (Leveson lens; `meta.no-redundant-gates`). Do NOT set the rule to error: that moves blocking authority into a suppressible surface (inline `eslint-disable`), which the lexical vitest test exists to outrank.

### Q5 — Ratchet interaction: counts vs markers

**Recommendation: counts STAY and markers add a second layer** (console-usage shape: exact per-file counts `:39-43` AND marker-required `:110-117`), plus one new cross-assertion: per-file `marked + unmarked == pinnedCount` and `unmarked == 0` at end-state (post-5b). Failure modes of each design — what a NEW unjustified read looks like:

| Design | New UNMARKED read | New read WITH self-authored marker | Moved/deleted site |
|---|---|---|---|
| **A. counts stay + markers (RECOMMENDED)** | vitest FAILS (count N+1 ≠ pinned N); eslint warns (unmarked > allowance) | vitest still FAILS until the JSON row is edited **in the same reviewed diff** — the conscious act survives | count change forces JSON edit; marker moves with its line → count catches it |
| B. counts shrink to unmarked-only | vitest FAILS (first unmarked site in a zero-unmarked file) | **passes silently** — marker is a comment authored by the same unreviewed hand; baseline drifts one PR at a time (normalization-of-deviance lens); also loses per-file totals as migration telemetry | silent (no count to trip) |
| C. markers only (drop counts at end-state) | FAILS (unjustified-site assertion) | **passes silently** — same self-service weakness as B, worse: no reviewed-file diff at all | silent |

B and C convert the ratchet's core property — *adding a sanctioned site is a reviewed act* — into self-service. The only argument for B (smaller JSON over time) is moot at ~44 rows. A's cost is deliberate duplication (counts + markers encode the same set), which the cross-assertion turns from drift-risk into a consistency check. Under A the eslint rule's count-mirror is permanently useful: it gives the count overrun an in-editor latency, not just CI.

## 4. Risks / open questions

- **Grain divergence lexical-vs-AST** (7 two-token lines today): mitigated by rule-side line dedup; residual risk is a future shape the AST sees but the regex doesn't (e.g. aliasing `const e = process.env; e.X` — invisible to BOTH the current regex on the `e.X` line and... actually visible at the alias line). The vitest scanner has the same blind spot today; unchanged by this slice. Name it in the rule's SCOPE header (catch/ssot precedent for honesty headers).
- **Marker quality floor vs 141 mechanical child-env markers:** floor forces ≥3 words — uniform forwards get formulaic text. Accepted: formulaic-but-true beats a magic word.
- **Block-severity choice:** adds the TAG_PATH line and ties the registry to the test; if the owner prefers the catch shape (warn-only row), drop `implementedBy`+block and the TAG edit — enforcement reality is unchanged either way (the vitest test blocks regardless). Owner call, presented both ways.
- **`env-allowed:` in-editor discoverability:** eslint-plugin unused-directive reporting is off in the fitness config (`eslint.config.fitness.mjs:96`) — a marker that outlives its site is caught by the vitest cross-assertions, not eslint. Fine (counts layer owns it).
